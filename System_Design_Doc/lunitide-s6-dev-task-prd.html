CHAPTER 01

以下运行实体把 DevTask 连接到真实开发过程；它们记录执行事实，但不替代磁盘内容和 Git 版本事实。

1.7 对话驱动开发闭环

  1. 绑定：用户选择工作区；检查信任、Git dirty、忽略规则和敏感文件。
  2. 理解：只加载任务来源、相关文件和必要记忆，不默认发送整个仓库。
  3. 计划：列出拟读取、拟修改文件和拟执行命令；Policy 为每个调用判级。
  4. 实现：写入前 checkpoint；patch 校验 base hash 后原子应用。
  5. 验证：运行 lint/test/build，必要时启动隔离浏览器预览。
  6. 审查：逐文件展示 diff、来源任务、增删行和诊断。
  7. 交付：CodeChange、TestRun、ScanRun、Evidence 与 TraceLink 齐全后进入 waiting_review。

1.7A 复杂代码任务的多 Agent 消费闭环（M6）

S6/M6 消费 M4 Agent Kernel 与 M6 受治理多 Agent 产生的 ComplexityDecision、PlanVersion、Parent/Child AgentRun、AgentResult；Child 生命周期、并发预算、取消/恢复和 JoinBarrier 由 M6 权威实现，S6 MUST NOT 建立领域私有执行核或更宽松策略。

M4/M6 通用输出S6 消费实体闭环要求
ComplexityDecision / PlanVersionDevSession / DevTask记录为何直答、单 Agent 计划或多 Agent；绑定不可变计划版本
Parent/Child AgentRunAssignment / ToolRun / 活动记录可映射前端、后端、DB、安全、QA 等逻辑分支，但不重新定义通用运行状态
AgentResult / JoinBarrierChangeSet / CodeChange / EvidenceChild 对主工作区只读，仅从隔离 staging/worktree 返回 PatchProposal + baseTreeDigest + Evidence；只有 Root WorkspaceMutationCoordinator 可按拓扑和 fencing sequence 串行重基/CAS/apply。文件重叠先冲突处理，最终合并树必须重跑 required test/scan，禁止子结果直接覆盖工作区
Tool / Test / Scan resultToolRun / TestRun / ScanRun形成不可变证据；required 测试、安全扫描或 Review 失败不得被其他分支成功覆盖
Checkpoint / Policy / ReviewDevSession.checkpoint_id / policy_decision_id / waiting_review写前恢复点和逐动作审批继续生效；Child 不继承审批 token、Secret lease 或临时 capability
完整完成条件：节点终态、证据、测试、安全检查、Review 与任务级验收必须同时满足；部分失败按 Plan 执行重试、降级或重新规划，并保留冲突和失败事实，不得以“多数 Child 成功”关闭任务。

1.8 工具权限矩阵

追踪铁律：需求 → 设计 → 任务 → 代码 → 测试 MUST 双向可追踪。任意链节缺失即视为流程缺陷，任务不得进入 ready_for_test。TaskSourceLink 是这条链的物理载体，CodeChange 与 TestCase 均须回指所属 DevTask。

CHAPTER 03

任务生成规则

开发管理专家 · DAG · 影响范围

开发管理专家（Dev Manager Agent）消费阶段一至五的产物：需求、方案、UI、DB Schema、接口规范，自动生成可执行的 DevTask 集合。

3.1 每个任务 MUST 满足

  1. 有来源链接和验收条件 — 通过 TaskSourceLink 指向至少一个上游产物，并在 description 中写明可验证的验收条件。
  2. 有依赖 DAG、影响范围和风险级别 — 写入 TaskDependency，标注影响模块与 blast radius，risk 取值 low/medium/high。
  3. 有负责逻辑角色 — Assignment.role 必须非空，actor_type 默认 agent，高风险任务默认 mixed。
  4. 绑定代码变更、测试与扫描结果 — 任务进入 waiting_review 前 CodeChange、TestCase、ScanRun 必须挂载齐全。

3.2 生成流程

[需求] [方案] [UI Mock] [DB Schema] [API Spec] │ │ │ │ │ └───────────┴──────────┴────────────┴───────────┘ ▼ 开发管理专家 (Dev Manager Agent) ▼ ┌─ 任务拆分 (按模块/层/职责) ├─ 依赖 DAG 构建 (拓扑排序 + 环检测) ├─ 影响范围与风险评级 ├─ 逻辑角色分配 └─ 来源链接回填 (TaskSourceLink) ▼ DevTask[] (写入 DB) ▼ 保留人工状态与已提交结果 ── 仅新增/更新 todo 项
禁止行为：任务不得因调整"开发人数标签"而重新分配进行中或已完成项，除非用户显式确认。开发人数标签仅影响新建任务的 actor_type 默认值与调度建议，不触发存量任务的状态回滚或 Assignment 重写。

3.3 风险评级标准

风险级别判定依据门禁强度
HIGH涉及密钥、鉴权、数据迁移、供应链依赖、Prompt 边界全门禁 + 独立安全批准或外部签名离线风险接受制品；否则阻断生产签发
MEDIUM涉及核心业务逻辑、跨模块接口、外部集成合并门禁 + 审查
LOW纯 UI 调整、文案、样式、文档基础 lint + unit

安全扫描

ScanRun · ScanFinding · 不可变证据

每次代码提交触发扫描运行，产出不可变证据。Critical 必须修复；High 必须修复或取得独立安全批准 / 外部签名离线风险接受制品。Agent 与提交 Owner 均不得自批解除生产签发门禁。

scajson依赖与许可证分析结果
secret_scanjson密钥/令牌泄露扫描结果

字段类型说明

4.3 扫描类型

类型目的阻断阈值

CHAPTER 07

测试策略

8 层次 · 核心验收矩阵

系统测试覆盖 8 个层次，从 Domain 单元到 Release 演练。High/Critical 扫描发现未关闭时 MUST 阻断，测试报告 MUST 绑定代码提交、依赖锁和规则版本。

7.1 测试层次

  1. Domain 单元测试 — 状态转换、规则、策略
  2. Contract — Bridge JSON Schema、RPC、模型协议、MCP/OData
  3. Repository / Migration — SQLite、约束、并发、恢复
  4. Integration — 真实或录制供应商、Worker、DPAPI
  5. UI E2E — WebView2 页面与 Bridge
  6. Security — XSS、SSRF、路径、命令、Prompt Injection、供应链
  7. Fault injection — 断网、429、磁盘满、崩溃、断电、坏包
  8. Release — 干净 Win10/11、升级、卸载、恢复

7.2 核心验收矩阵

Key除主动输入窗口外，已保存 Key 不返回 Renderer；配置/DB/log/diagnostic/crash dump 及提交后稳定内存扫描 0 明文；正式接口无 reveal-key

CHAPTER 08

质量门禁

合并门禁 · 发布门禁 · 豁免规则

门禁分两层：合并门禁在 PR 合并时强制，发布门禁在发布包签发时强制。Critical 默认不可豁免；High 必须满足下述风险接受规则，否则阻断流转。

合并门禁 Merge Gate

每次 PR 合并到主分支前必须全部通过：

  • 格式 — 代码格式化检查（prettier / gofmt）
  • lint — 静态 lint 规则零警告
  • unit — 单元测试 100% 通过
  • contract — Bridge / RPC / MCP / OData 契约测试通过
  • race — 竞态检测（-race）无报告
  • SAST — 静态安全扫描无未豁免高危
  • secret scan — 密钥扫描零命中

发布门禁 Release Gate

发布包签发前必须全部通过：

  • 全套 E2E — UI E2E + Integration 全绿
  • 安全 — Security + SCA 全套，供应链核查
  • 迁移 — DB 迁移正向 + 回滚演练
  • SBOM — 软件物料清单生成并归档
  • 签名 — 包体与摘要签名验证
  • 干净机恢复 — 干净 Win10/11 安装/升级/卸载/恢复演练
阻断红线：Critical 一律阻断；High 在没有合格独立安全角色或离线风险接受制品时 MUST 阻断生产签发。Agent 不得自动跳过、自动标记 false_positive 或自动 waive。
