S7 · CR 与发布部署 PRD

阶段：九 · CR / 发布 / 部署 域：Release & Deployment 基线：v1.0 状态：M7 目标设计；M0 安装 POC / M2 Alpha 安装 / M7 生产门禁

本 PRD 定义 Lunitide 月汐的变更请求（CR）与发布部署体系。CR MUST 绑定 Git 提交、依赖 CR DAG、 测试证据、制品 SHA-256、版本、目标环境和回退策略；并以乐观并发、Git 三方合并、不可变发布包和同 digest 环境晋级贯穿协作与交付。审批后任一绑定内容改变即自动进入 changed_after_approval 须重新审批。

核心原则：Lunitide 自身更新 与 用户项目部署 是两个独立领域，使用不同枚举与表， 不共用含糊的版本/回滚承诺。多人开发禁止长期悲观代码锁与 last-write-wins；仅不可变 ReleasePackage 冻结及目标环境导入使用 TTL 短租约。所有发布实体遵循严格状态机与环境门禁。

CHAPTER 01

变更请求（CR）模型

实体：7 张表

发布域由 7 个核心实体组成。CR、Deployment 与应用自身 Update 使用不同枚举与表， 严格分离以避免跨域版本/回滚承诺混淆。

1.1 ChangeRequest 实体

ChangeRequest 是发布链路的业务容器，承载意图、目标版本与当前修订引用；CRRevision 才是审批、冻结、内容漂移和 ReleasePackage 绑定的唯一权威。下表的 submitted/approved/changed_after_approval/packaged 是由 current_revision 投影的兼容展示状态，不得形成第二套可独立写入的审批状态机。

字段类型说明
idstring (CR_*)CR 唯一标识，全局唯一，不可变
project_idstring所属项目 ID，绑定命名空间与权限域
titlestring变更标题，面向人类可读
descriptiontext变更意图、影响范围、回退预案描述
statusenumdraft/submitted/approved/rejected/changed_after_approval/packaged/released/withdrawn
versionstring (semver)目标发布版本号，遵循语义化版本
target_environmentref → Environment目标部署环境引用
rollback_strategyenum回退策略：binary / schema / data / external
created_attimestamp创建时间，用于审计与排序

1.2 CRDependency 实体

构建 CR 之间的有向无环依赖图（DAG），用于影响传播与编排顺序。

字段类型说明
cr_idref → ChangeRequest当前 CR 引用
depends_on_cr_idref → ChangeRequest被依赖的 CR，禁止形成环
conditionenum依赖条件：requires / requires_succeeded / parallel_with

1.3 ReleasePackage 实体

CR 经审批后产出的可部署制品包，绑定构建 ID 与整体摘要。

字段类型说明
cr_idref → ChangeRequest所属 CR
sha256string (hex)包整体 SHA-256 摘要
artifact_typeenum制品类型：binary / container / static_assets / migration_bundle
build_idstring构建流水线 ID，可追溯到 CI 产物
sizeint64包字节数，用于配额与完整性校验

1.4 ArtifactDigest 实体

包内单制品的摘要记录，支持逐件校验与差异影响分析。

字段类型说明
package_idref → ReleasePackage所属制品包
artifact_namestring制品相对路径或名称
sha256string (hex)单制品 SHA-256 摘要
algorithmenum哈希算法：sha256（v1 唯一支持）

1.5 Environment 实体

目标部署环境的定义，承载配置引用与运行状态。

字段类型说明
namestring环境名称，如 production / staging
typeenum环境类型：dev / staging / production / dr
config_refref环境配置快照引用，版本锁定
statusenum状态：active / maintenance / decommissioned

1.6 Deployment 实体

CR 在目标环境的一次实际部署执行记录。

字段类型说明
cr_idref → ChangeRequest触发本次部署的 CR
environment_idref → Environment目标环境
statusenumpending/running/succeeded/failed/rollback_pending/rolling_back/rolled_back/rollback_failed
started_attimestamp部署开始时间
ended_attimestamp部署结束时间（含回退完成）
strategyenum策略：full（整体部署） / partial（局部部署）

1.7 RollbackAttempt 实体

对一次 Deployment 发起的回退尝试记录，与部署本身分离。

字段类型说明
deployment_idref → Deployment被回退的部署
statusenumpending/running/succeeded/failed
strategyenumbinary / schema / data / external
started_attimestamp回退开始时间
ended_attimestamp回退结束时间
域分离原则：CR、Deployment 与应用自身 Update 使用不同枚举与表。 不得将"用户项目部署"的状态与"Lunitide 自身更新"的状态混入同一张表。
CHAPTER 02

CR 状态机

8 个状态

CR 在生命周期中流转于 8 个状态之间。审批是关键门禁：通过后进入 approved， 任意绑定内容改变将自动回退到 changed_after_approval 须重新审批。

2.1 状态枚举

自动状态转换：审批后任一绑定内容（Git commit、依赖 DAG、测试证据、制品 SHA-256、 版本、目标环境、回退策略）发生改变，CR 自动进入 changed_after_approval。
强制重审：changed_after_approval 须重新审批，不得沿用旧批准直接打包或发布。 系统禁止静默绕过此门禁。
CHAPTER 03

CR 绑定要求

绑定：7 项 MUST

每个 CR MUST 绑定以下 7 项内容。绑定完整性是审批与打包的前置条件；任一缺失或哈希不匹配， CR 不得进入 approved 之后的任何状态。

1. Git Commit

绑定具体 commit SHA，作为代码来源的唯一锚点。提交变更触发 CR 状态迁移。

2. 依赖 CR DAG

声明 CR 间依赖关系（CRDependency），禁止成环。依赖 CR 状态变化向上传播。

3. 测试证据

绑定 TestEvidence 引用集合，覆盖单元、契约、E2E 与安全扫描结果。

4. 制品 SHA-256

绑定 ReleasePackage 与 ArtifactDigest 摘要，逐件校验完整性。

5. 版本

声明目标 semver 版本号，与 Git tag 与制品元数据一致。

6. 目标环境

绑定 Environment 引用，锁定部署目标与配置快照。

7. 回退策略

声明 rollback_strategy（binary / schema / data / external）， 指明失败时的回退路径与不可逆操作的处理预案。

绑定完整性门禁：审批前系统 MUST 校验全部 7 项绑定存在且哈希自洽。 打包阶段再次校验绑定哈希未发生漂移；任一不一致即标记 changed_after_approval。

4.3 部署策略

整体部署（full）

对目标环境进行完整替换式部署。适用于全量发布、破坏性变更或环境初始化。 要求回退策略完备且已通过演练。

局部部署（partial）

仅部署变更涉及的子集制品，保留其余部分不变。适用于热修复、配置调整、 单服务迭代。须声明影响的制品范围与不变性约束。

绑定变化门禁：任意制品摘要、提交、依赖或测试证据变化使 approved CR 进入 changed_after_approval。已 packaged 的 CR 若绑定漂移， 禁止触发 Deployment；运行中的 Deployment 不得因绑定变化静默中断。
CHAPTER 05

Review 与审批

强制确认：5 类

运行模式（手动 / 半托管 / 全托管）只影响低/中风险操作的自动化程度。 以下高风险操作即使全托管也 MUST 经人工确认，不得自动执行。

5.1 强制确认操作

1. 发布与部署类

push、发布、生产部署。任何将变更推送到生产环境的操作。

2. 破坏性数据操作

破坏性数据库或文件操作，包括 drop、truncate、覆盖、批量删除。

3. 凭据与敏感数据

凭据导出、跨域发送敏感数据。涉及 Key、Token、PII 的跨边界流转。

4. 代码与权限

执行未信任代码或扩大技能权限。包括新 Skill 安装、Tool 权限提升。

5. 安全策略与信任根

修改安全策略、审计或更新信任根。涉及 Policy Engine、审计日志、根证书与签名链。

5.2 Review 绑定字段

每次 Review 创建时 MUST 绑定以下字段，作为审批的精确锚点。

字段说明
operation_type操作类型，如 deployment.execute
params_hash规范化参数哈希（SHA-256），参数变化即视为新请求
resource目标资源引用（type / id / version）
plan_version计划版本，绑定 Plan 快照
policy_version策略版本，绑定 Policy Engine 快照
risk风险等级：low / medium / high / critical
expires_at批准过期时间，超时即失效
// Review 创建示例 { "operation": "deployment.execute", "resource": {"type":"deployment","id":"dep_123","version":3}, "normalizedParams": { "environment": "production", "artifactSha256": "...", "mode": "partial" }, "paramsHash": "sha256:...", "planVersion": 7, "policyVersion": 12, "risk": "critical", "expiresAt": "2026-08-09T11:00:00Z" }
参数哈希失效：参数变化后旧批准失效。params_hash 是审批的精确指纹， 任何规范化参数差异都将使既有批准作废，必须重新发起 Review。
超时默认拒绝：超时默认保持暂停或拒绝，绝不自动执行。 即使全托管模式，过期的高风险批准也不得被静默续期或自动放行。
CHAPTER 06

回退策略

4 种回退维度

回退不是单一操作。二进制回退与 schema/data 恢复分开处理， 外部副作用需独立补偿。回退策略在 CR 创建时声明，部署失败时按策略执行。

6.1 回退维度

维度说明可逆性
binary回退二进制制品到上一版本目录高（保留上一版二进制）
schema回退数据库 schema 迁移受 migration compatibility 声明约束
data恢复数据到 checkpoint 快照取决于备份与写穿范围
external补偿外部系统副作用（API 调用、消息）可能不可逆，需人工补偿

6.2 回退启动条件

Migration Compatibility 声明

只有当 migration compatibility 声明允许时，才能启动旧二进制。 若新版本执行了不可逆 schema 迁移（如 drop column），旧二进制不得直接启动， 须进入 recovery_required 模式由人工评估。

CHAPTER 07

两个独立域

用户项目部署

8.2 签名验证规则

双重要求

安装器、二进制和更新 manifest 必须 Authenticode / 独立签名 与 SHA-256 验证。 两者缺一不可：签名保证来源可信，SHA-256 保证内容完整。

  • 证书轮换需双签过渡，新旧证书并存直至全部客户端升级
  • 构建生成 SBOM 和制品证明，随包分发
  • React 静态资源嵌入或随签名包分发并校验 hash

8.3 防降级与防重放

防降级

记录最低允许版本 minimumAllowedVersion。 禁止降级到低于该阈值的版本，防止攻击者通过旧版漏洞绕过修复。

防重放

manifest 包含时间戳与 nonce，校验时拒绝过期或已使用的更新包。 活动高风险任务未 checkpoint 时禁止强制更新。

禁止降级：禁止降级到低于 minimumAllowedVersion。 活动高风险任务未 checkpoint 时禁止强制更新，须等待任务完成或显式中断后再执行。
迁移失败处理：迁移失败不得继续启动新版核心业务，应进入 recovery_required， 允许导出诊断、恢复备份或回到兼容旧二进制。
CHAPTER 09

发布前总验收

附录 B · 验收清单

以下为发布前总验收清单（附录 B）。所有项 MUST 全部通过方可发布； 任何未豁免的 Critical/High 阻断发布。

9.1 核心验收清单

  • 正式包无运行时依赖：正式包无 Electron / Node runtime / Python / FastAPI / PyInstaller；Go/WebView2 架构图、进程和安装产物一致。
  • Key 全路径扫描 0 明文：除用户正在输入且尚未提交的受控窗口外，已保存 Key 不得返回 Renderer；配置、DB、日志、诊断包、崩溃转储及提交后的稳定内存扫描 0 明文 Key。
  • Bridge 无通用本机能力：Bridge 不暴露通用本机执行能力，仅提供受控的窄接口。
  • Provider 真实测试通过：OpenAI-compatible、Anthropic 两协议族真实契约测试和错误矩阵通过。
  • 九阶段状态与 stale 传播：九阶段状态、产物快照和 stale 传播通过；上游修订 MUST 将下游标记为 stale，禁止静默替换输入。
  • 高风险 100% 审批：高风险 100% 审批且防重放 / TOCTOU；Skill/Tool 隔离及 Prompt Injection 测试通过。
  • CR 门禁通过：CR 测试 / 审批 / 摘要 / 依赖门禁通过；模板/底座版本锁定、兜底、删除保护通过。
  • Authenticode 签名有效：Authenticode、manifest 签名、SBOM 与 hash 有效；迁移、备份、恢复、坏更新故障注入通过。
  • Win10/11 干净机验证：Win10/11 干净机安装、升级、卸载验证通过；P95 可交互 ≤ 5 秒，0 孤儿进程。
质量门禁说明：合并门禁含格式、lint、unit、contract、race、SAST、secret scan； 发布门禁含全套 E2E、安全、迁移、SBOM、签名、干净机和恢复演练。 豁免须 Owner + 安全理由 + 到期时间。

NORMATIVE ADDENDUM

并发安全、环境晋级与代码 + 数据库同包发布

分阶段基线
范围裁决：v1 仍是单一自然人用户，ADR-011 仍为 Deferred。M0–M7 MUST 实现的是本机用户、Agent、VS Code、文件监视器之间的 base hash / version、CAS、三方合并、不可变修订与短租约；多人身份、Presence 传输、实时协作、N-of-M 审批和职责分离属于未来协作版，不得作为 v1 发布前置条件。下文的 actor / owner_id / presence 字段仅作前向兼容数据模型；v1 actor 固定为本机 Owner 或有明确类型的系统主体。

11.1 实体、并发编辑与 CR 汇总

实体关键字段不变量

11.2 轻量 SAP Transport 与租约边界

固定链路：ChangeTask → CR Revision → 不可变 ReleasePackage → 同一 digest 按开发 → 测试 → 生产晋级。开发环境本地/工作区生效不算传输；开发 + 生产 = 1 次晋级，开发 + 测试 + 生产 = 2 次晋级。
  • 环境门禁：development 验证成功方可晋级；配置 test 时必须 test 成功、证据齐全后方可 production；未配置 test 时可 development → production，禁止任意跳级。
  • Promotion 校验来源环境成功、digest 未变、目标策略和审批哈希有效；生产导入还须满足维护窗、恢复点能力与生产批准。v1 单用户模式采用 Owner 二次强确认、OS 身份重认证或冷却期，不伪造双人职责分离；N-of-M/职责分离仅在未来协作 capability 启用后成为门禁。
  • 仅冻结 ReleasePackage 和目标环境导入可获取有 TTL 的短时 Lease；到期自动释放，重试使用幂等键并重验状态。
  • 租约不覆盖日常编辑、Review 或人工等待；系统按依赖与资源能力调度，不宣称真正同时并行执行。

Promotion：pending → gated → preflight → importing → verifying → succeeded；门禁拒绝进入 blocked，失败进入 failed 或 rollback_required，结果不明进入 outcome_unknown；部分成功不得记为 succeeded。

11.3 代码与数据库同包及发布编排

ReleasePackage 必须绑定 代码、DatabaseContract、MigrationPackage、IntegrationVersion、证据和回退方案，统一纳入 package digest；冻结后不得原位修改，只能创建新 CR Revision 与新包。其版本化 canonical manifest MUST 固定 UTF-8/NFC、字段顺序、长度前缀与哈希算法版本，并记录 package_id、CRRevision、每个成员的 type/digest/size、SBOM/provenance、签发者与冻结时间；冻结后 DB 约束拒绝 UPDATE/DELETE/追加成员。

#步骤门禁 / 失败语义
1Preflight 只读契约检查校验 schema、权限、容量、版本、锁风险与契约；失败零写入终止
2恢复点备份/checkpoint 可验证并记录 ID；不能建立则禁止继续

11.4 审批哈希、失败与审计

审批摘要：approval_hash = SHA-256(revision_manifest + package_digest + code_digest + database_contract_digest + migration_digest + integration_version_digest + evidence_digest + rollback_plan_digest + promotion_path + target_environment + policy_version)；界面展示风险、破坏性步骤、职责分离、环境路径、证据与回退摘要；冻结及每次晋级前重算，漂移即失效。

  • 迁移超时/结果未知：进入 outcome_unknown，停止代码部署并先对账；禁止盲目重跑非幂等步骤。
  • 迁移成功而代码失败：仅按兼容窗口回退/保留旧代码；数据库不默认逆迁移。
  • 健康/契约失败：环境标记 degraded，阻止后续晋级并记录恢复点、实际 digest、补偿及人工裁决。
  • 冲突、合并、状态迁移、审批哈希、租约、preflight、迁移输出摘要、部署、复核和回退全部写 append-only AuditEvent；敏感值仅记脱敏摘要。

11.5 应用自身 Schema、备份、恢复与卸载基线

  • 应用自身迁移使用 appSchemaMigration.*，用户项目迁移使用 projectMigrationPackage.*；Renderer 不得直接调用通用 migration.run。项目迁移只能由 Promotion / ReleaseRun 内部命令以 releasePackageDigest、migrationDigest、targetEnvironmentId、approvalHash 和 fencingToken 执行。
  • 迁移文件必须带编号、checksum 和 minimum app version；升级前检查磁盘并创建 SQLite、WAL、内容寻址资产和必要索引元数据的一致性备份。可事务化步骤在事务内执行，其他步骤使用 durable journal。
  • 迁移后执行 integrity_check、foreign_key_check、关键行数/hash；失败进入 recovery_required，禁止继续写业务数据。
  • 默认每日备份，并在关键升级/发布前立即备份；介质或数据库损坏 RPO 等于最近成功备份间隔，人工恢复路径 RTO 建议 ≤30 分钟。默认保留最近 7 个日备份和 3 个升级前备份。
  • 备份必须加密、认证并受当前用户 ACL 保护，密钥使用 DPAPI CurrentUser 包装；manifest 绑定 schema/app version、数据与资产 digest、tombstone high-water mark。恢复先在隔离 staging 验签、验链、迁移并重放墓碑，再原子切换。
  • 错误用户、密钥丢失、空间不足、篡改、旧 schema 不识别墓碑均 fail-closed 并给出不可恢复/诊断路径。项目导出不包含凭据，导入后必须重新绑定。
  • 卸载默认保留用户数据；“同时彻底删除”必须是独立显式选项并警告不可恢复。安全版本下限不得因 recovery 被绕过。
