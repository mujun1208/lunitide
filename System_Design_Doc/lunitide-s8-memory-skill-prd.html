Part 1 / Memory System

第一部分 · 记忆系统

CH 01 — CH 05

Memory Manager 负责记忆的生命周期管理：写入分级、来源追溯、可信度标注、重要度评估、 召回解释与删除传播。所有记忆按四层分层存储，确保时间连续性与跨会话一致性。

CHAPTER 01

四层记忆模型

Lunitide 将记忆统一划分为四层：working / short_term / long_term / semantic。每一层有不同的生命周期、写入门槛与召回权重，共同保证 Agent 在时间维度上的连续性。

Layer 1 · Working
工作记忆
当前 run 的临时状态，包括本次推理的中间变量、工具返回的暂存结果、尚未提交的计划节点。
生命周期：run 结束自动清理
Layer 2 · Short-term
短期记忆
会话摘要与近期交互片段，支撑上下文窗口内的连贯对话，会话结束后归档或遗忘。
生命周期：会话结束归档 / 遗忘
Layer 3 · Long-term
长期记忆
用户确认的事实、偏好、决策与情节。只有经用户确认的内容才可进入此层，持久化存储。
生命周期：持久化，可修订 / 删除
Layer 4 · Semantic
语义记忆
由本体（ontology）或事实结构化出的知识图谱节点，提供可推理、可关联的结构化知识。
生命周期：本体维护，版本化
层级关系说明：四层并非简单的"时间长短"划分，而是可信度与持久化承诺的递进。 Working → Short-term 的派生记忆条目属于可按 TTL 清理区间；Long-term → Semantic 属于"已确认可信赖"区间。原始 Message 是独立事实源，不因 short_term 清理或上下文压缩而删除。 越往深层，写入门槛越高、删除传播范围越广、召回权重越稳。

情节记忆不是第五层

情节记忆（episodic memory）作为 kind=episodic 的长期记忆存在，而非独立的第五层。它记录"何时、何地、发生了什么"的事件序列，与 kind=fact（事实）、kind=preference（偏好）、kind=decision（决策）并列，共享 long_term 层的写入门槛与安全约束。

设计意图：避免"五层"造成层级膨胀。情节性只是记忆内容的一种 kind，分层维度保持正交—— layer 回答"存多久、多可信"，kind 回答"是什么类型的内容"。
CHAPTER 02

记忆实体设计

记忆系统由五个核心实体构成，分别承载记忆条目、来源追溯、修订历史、召回日志、删除墓碑。

2.1 memory_entry — 记忆条目

记忆的主实体，每一条记录代表一条可被召回的记忆单元。

字段类型说明
idULID记忆唯一标识
workspace_idULID所属工作空间，隔离边界
project_idULID所属项目，作用域粒度
layerenumworking / short_term / long_term / semantic
kindenumfact / preference / decision / episodic / summary …
content_refref内容引用（结构化记录 + 向量索引）
confidencefloat可信度 [0,1]，用户确认 = 1.0
importancefloat重要度 [0,1]，影响召回权重
statusenumactive / archived / deleted
ttl_attimestamp过期时间，working/short_term 有效
revisionint修订版本号，单调递增

2.2 memory_source — 记忆来源

每条记忆必须可追溯到其来源，来源类型包括用户消息、工具输出、模型推断、外部导入等。

字段类型说明
memory_idULID关联记忆条目
source_typeenumuser_message / tool_output / model_inference / import
source_idULID来源消息 / 工具调用 / 推理记录 ID
source_revisionint来源内容的版本快照
quote_reftext原文引用片段，支撑召回解释

2.3 memory_revision — 记忆修订

长期记忆可被修订，每次修订记录旧值、新值、原因与操作者，形成完整审计链。

字段类型说明
idULID修订记录标识
memory_idULID被修订的记忆条目
old_refref修订前内容引用
new_refref修订后内容引用
reasontext修订原因
actorenumuser / agent / system
timetimestamp修订时间

2.4 recall_event — 召回事件

每次记忆召回都会记录一条事件，用于召回质量分析与召回链路审计。

字段类型说明
idULID召回事件标识
session_idULID发起召回的会话
query_hashhash召回查询的哈希，便于去重分析
memory_idULID被召回的记忆条目
scorefloat综合召回得分
rankint本次召回中的排序

2.5 deletion_tombstone — 删除墓碑

删除分为内容清除和最小审计墓碑：事务提交墓碑时，源对象同时变为不可读，所有读取、召回、摘要装配和 Handoff 导入路径 MUST 立即 fail-closed；随后异步物理清除原文、content_ref、向量、缓存和全部递归派生内容。仅可保留不含原文、摘要、向量或可逆标识的最小审计墓碑。

字段类型说明
owner_typeenummemory_entry / skill / tool 等
owner_idULID被删除对象标识
deleted_attimestamp删除发起时间
propagation_statusenumpending / propagating / completed / failed
实体关系总览： memory_entry 1—N memory_source（一条记忆可有多个来源）， 1—N memory_revision（修订历史）， 1—N recall_event（被多次召回）， 删除时生成 1 条 deletion_tombstone 并传播。
CHAPTER 03

记忆写入与分级规则

Memory Manager 在写入时必须为每条记忆标注来源、作用域、可信度、重要度与修订记录，并根据内容性质归入对应层级。写入门槛随层级递进升高。

3.1 写入分级规则

层级写入门槛典型内容可信度来源
working无门槛，run 内自动写入中间变量、工具暂存结果不标注，run 结束清理
short_term会话内自动摘要近期交互片段、会话摘要模型生成，标注低可信度
long_term需用户确认事实、偏好、决策、情节用户确认 = 1.0
semantic本体校验 + 结构化知识图谱节点、关系本体权威性决定

3.2 每条记忆的必备属性

  • 来源（source）：必须可追溯到 user_message / tool_output / model_inference / import 之一，记录 quote_ref 原文引用。
  • 作用域（scope）：workspace_id + project_id 双重隔离，决定可见范围与召回边界。
  • 可信度（confidence）：[0,1] 浮点，用户确认 = 1.0，模型推断 < 1.0，影响召回权重。
  • 重要度（importance）：[0,1] 浮点，由内容性质与用户行为信号综合评估。
  • 修订记录（revision）：每次修订生成 memory_revision，记录 old_ref / new_ref / reason / actor。
关键约束：模型推断不能自动升级成"已确认事实"。模型生成的内容只能写入 short_term 并标注低可信度； 升级到 long_term 必须经过用户显式确认，且 confidence 设为 1.0。这一约束防止幻觉被固化为"记忆"。
升级路径：short_term → long_term 是一条单向、需确认的路径。 当模型识别出"可能值得长期记住"的内容时，将其作为候选暂存于 short_term，并向用户发起确认请求； 用户确认后方可写入 long_term。未被确认的候选在会话结束后按遗忘策略清理。
核心原则：只有用户确认的事实才能进入 long_term。这是 Lunitide 记忆系统可信性的基石—— long_term 层的每一条记忆都带有"用户背书"，召回时可信赖，不会把模型的一次推断当作既定事实。
CHAPTER 04

上下文压缩、续接与记忆召回

会话上下文与长期记忆是两套相关但不同的机制：上下文压缩负责在同一任务中保留完整脉络，Context Handoff负责把工作态续接到新会话，记忆召回负责按需引入跨会话事实。三者不得互相替代。

4.1 百万 token 逻辑上下文

  • 单个 Session MUST 可累计、分页、索引并重建至少 1,000,000 tokens 的原始消息、工具引用与附件引用。
  • 逻辑上下文不等于模型物理窗口。32K、128K、200K 或更大窗口模型均由 Context Builder 构造适配后的本轮请求。
  • 原始 Message 是事实源且默认 append-only；分段摘要、滚动摘要和 Handoff 都是可失效、可重建的派生视图。
  • 单页消息数、Bridge frame、RPC payload 和 Renderer 虚拟列表上限只限制一次传输/渲染，不得限制会话累计规模。

4.2 分层压缩与触发

层处理方式保留策略
近期原文保留最近消息和当前任务相关原文最新用户输入、系统约束、活跃审批不得摘要替代
Segment Summary对稳定 message sequence 区间做增量摘要每段绑定 source digest、起止 sequence 和 token 数
Rolling Summary合并多个分段摘要，形成可回退摘要树引用 parent summary IDs，不递归丢失来源
外置内容大工具输出、日志、文件全文保存为 ArtifactRef提示中只放摘要、hash、范围和按需读取入口

请求预算利用率采用架构统一公式：有效窗口扣除 tokenizer 安全余量，requiredTokens 同时计入 system、tool schema、选定上下文、当前输入、最大输出和工具续接预留。70% 仅预生成 draft，校验通过成为 validated；自动模式 85% 可 CAS 激活。手动“压缩上下文”先 preview，只有显式 commit 才激活。95% 强制先压缩并重新预算；仍超限返回 CONTEXT_BUDGET_EXCEEDED，不发送越窗请求。

4.3 摘要保真、版本与失败语义

每个摘要/Handoff 使用固定结构，而不是一段无约束自由文本：

  • goal_and_state：目标、当前阶段、已完成事项；
  • decisions：关键决策、理由、替代方案及来源；
  • constraints：用户硬约束、安全边界、禁止事项；
  • open_tasks：未完成任务、阻断、负责人/下一步；
  • code_refs：workspace、Git SHA/checkpoint、文件、行范围、symbol 与 content hash；
  • tool_and_evidence：命令、测试、构建、浏览器证据及结果引用；
  • risks_and_unknowns：风险、假设、仍需确认事项。

每个事实性、状态性、决策性、约束性、任务性和证据性 claim 必须关联至少一个叶级 Message/ToolResult/Artifact revision；建议/推断必须标记 claim_type 并保存 derivation sources，不得展示为已确认事实。生成后执行 schema、来源/digest/作用域、数字/路径/符号、未完成任务和硬约束覆盖校验；仅指向 parent summary 不算溯源完成。fidelityReport 至少返回 claim 总数、验证数、缺失来源数、冲突数、硬约束与 open-task 覆盖率。校验失败标记 rejected；压缩采用 baseVersion 乐观并发，失败保留上一 active version并重新预算，不得静默截断。

4.4 Context Handoff：续接到新对话

当窗口接近上限、用户主动切换话题或需要并行分支时，可从当前会话生成不可变 Handoff。它记录 workspace/project、source_session_id、source_seq_start/end、source_digest、summary/schema version、项目/任务/计划/checkpoint 引用和上述结构化内容。create 在同一快照读取闭区间并计算 digest；import 重验 scope、range、digest 和墓碑，默认拒绝跨项目导入。目标会话导入前展示摘要、来源范围与差异；导入后建立 parent/child 关系，可一键回到原文查证。

禁止语义：Handoff 不是复制整段聊天，也不是把低可信长期记忆冒充当前任务事实；它不得自动继承审批授权、Secret、临时 capability token 或已过期工具权限。

4.5 Token 节省策略

  • 稳定 system/tool 前缀保持确定顺序以利用供应商 prompt cache；缓存命中只作为优化，不影响正确性。
  • 按符号、引用闭包和 diff 读取代码；相同 content hash 不重复注入全文。
  • 工具大输出外置，优先注入结构化结果和可按需展开引用；失败日志先去重再摘要。
  • 摘要按新增稳定区间增量生成，不反复总结完整历史；摘要树允许针对当前任务只展开相关分支。
  • 记忆采用 BM25 + 向量 + 时效/重要度/可信度混合召回，并设置独立 token 配额，避免挤占近期对话。
  • 容量采用固定版本 canonical tokenizer；本轮预算采用模型 tokenizer 并以真实 usage 回校。记录 canonical/request/cached/output tokens、tokenizer version、消息/字节/附件量和压缩节省率。

4.7 验收与回归基线

测试必须满足
1M 长会话 corpus累计至少 1,000,000 tokens 后仍可按 cursor 查看任意历史范围、生成新消息、重启恢复并重建 active summary；不得出现固定消息总数截断
窗口矩阵同一 corpus 在 32K / 128K / 200K 能力模型下均不超窗；保留输出预算，切换小窗口不静默丢弃约束

并发与失败注入压缩期间追加消息、模型超时、摘要格式错误、数据库重启均不替换最后可用版本，不丢原消息
Handoff E2E新会话恢复目标、状态、待办、checkpoint 和文件符号；不继承审批、Secret 或临时权限；可返回源范围查证

4.8 召回综合因素

因素权重维度说明
相关度语义相似 + 关键词命中向量相似度与词项匹配的加权融合
时效时间衰减越近期的记忆权重越高，长期记忆衰减更慢
重要度importance 字段写入时标注的重要度直接参与评分
可信度confidence 字段用户确认的记忆优先于模型推断

4.9 返回解释

每次召回不仅返回记忆内容，还返回为什么召回这条记忆的解释——包括命中的因素、得分构成与来源引用（quote_ref）。解释能力让召回过程可审计、可调试，也支撑 UI 上的"记忆溯源"展示。

4.10 RecallEvent 召回日志

每次召回写入一条 recall_event，记录 session_id、query_hash、memory_id、score、rank、injected_tokens、time。这些日志用于：

  • 召回质量分析：统计命中率、排序合理性、低质量召回占比。
  • 上下文预算管理：追踪 injected_tokens 累积，防止记忆注入挤占模型上下文。
  • 召回链路审计：回答"这条记忆是在什么会话、什么查询下被召回的"。

4.11 injected_tokens 注入限制

召回的记忆会被注入到模型上下文中，但注入量受 injected_tokens 上限约束。当召回结果超出预算时，按 rank 裁剪低分记忆，确保不挤压用户当前输入与系统指令的空间。

召回质量保障：召回综合相关度、时效、重要度和可信度，并返回解释。 这意味着每一条进入上下文的记忆都是可解释、可追溯、有依据的—— 模型不仅能"记住"，还能说清"为什么在这个时刻想起这条"。
CHAPTER 05

记忆安全与隔离

记忆承载用户隐私与项目机密，安全隔离是不可妥协的硬性要求。Lunitide 在作用域隔离、删除传播两方面建立完整机制。

5.1 跨项目隔离

每条记忆绑定 workspace_id 与 project_id，召回查询始终携带作用域过滤，确保 A 项目的记忆永远不会出现在 B 项目的上下文中。

硬性约束：跨项目 Memory 泄漏率必须为 0。 这是安全底线，不是"尽力而为"的指标——任何导致跨项目记忆泄漏的路径都被视为缺陷。 召回链路在向量检索、结果过滤、上下文注入三个环节均强制携带作用域校验。

5.2 删除传播

压缩不是删除。自动/手动压缩、归档、模型切换和 Handoff 均不得触发源 Message 删除。只有用户显式删除或已生效的合规保留期策略可以创建删除墓碑；墓碑创建与源对象不可读在同一事务完成。所有 pending/propagating/failed 状态均禁止注入，之后递归清除重叠摘要、Handoff、目标会话再派生摘要/记忆、向量、缓存、context_build manifest 和内容寻址资产。

记忆删除不是单点操作，必须传播至所有承载该记忆的存储与派生数据。一条长期记忆可能同时存在于：

  • 结构化记录：memory_entry 行记录及其关联的 source / revision。
  • 向量索引：用于语义召回的 embedding 向量。
  • 缓存：召回结果缓存、会话上下文缓存。
  • 摘要：已生成的会话摘要、长期摘要中引用该记忆的片段。

5.3 DeletionTombstone 传播机制

删除时生成一条 deletion_tombstone，记录 owner_type / owner_id / deleted_at / propagation_status。传播状态机为：

pending
→
propagating
→
completed
↯
failed

propagation_status: pending → propagating → completed（失败时 failed，触发告警与重试）

传播过程逐项物理清理结构化内容、向量、缓存、摘要和递归派生物，每完成一项更新 propagation_status。只有所有目标都完成清理，墓碑状态才置为 completed；任一失败则置为 failed 并告警重试，但绝不恢复可读。备份可按合规期限延迟清除，但恢复时必须先重放墓碑再开放读取。

删除的彻底性：删除需传播至结构化记录、向量、缓存和摘要。 这意味着一条被删除的记忆不会残留在任何可被召回的路径中—— 既防止"幽灵记忆"被召回，也满足隐私合规的"被遗忘权"要求。

CHAPTER 06

CHAPTER 08

技能状态机

技能从草稿到卸载经历七个状态，每个状态转换都有明确的触发条件与校验要求。状态机确保技能生命周期可控、可审计。

8.1 七状态定义

状态含义是否可执行
draft草稿，Manifest 编辑中，未校验否
validated已通过 Manifest 完整性与签名校验否
installed已安装到工作空间，尚未启用否
enabled已启用，可被匹配与触发是
disabled已禁用，暂停触发但保留安装否
quarantined隔离，因安全风险暂停，需人工审查否
uninstalled已卸载，安装记录归档否

正常路径：draft → validated → installed → enabled ⇄ disabled → uninstalled ｜ 安全路径：installed/enabled → quarantined → uninstalled

隔离触发条件：未签名或权限扩大的升级默认 quarantined。 当一个新版本的 signature_status 为 invalid，或其 permissions_json 相比已安装版本出现权限扩张时， 系统不自动启用，而是将其置入隔离态，等待人工审查与显式授权。这防止"静默提权"——技能通过版本升级悄悄获取更高权限。
状态机设计意图：七个状态覆盖了技能从"编辑"到"退役"的完整生命周期。 正常路径是单向递进的（draft → ... → enabled），而 quarantined 是一个"安全闸"—— 任何可疑的升级或行为异常都会把技能拉回隔离态，阻断其继续执行，直到人工裁定。
CHAPTER 09

技能匹配决定"在当前对话中，应该考虑哪些技能"。匹配策略遵循显式触发优先、语义评分其次，并对结果做阈值过滤与冲突消解。

9.3 SkillTrigger 记录匹配过程

每次匹配写入 skill_trigger，记录 score、reason（显式命中 / 语义高分 / 用户选择）、status（matched / executed / skipped / denied）与 result_ref。这些记录支撑：

  • 匹配质量分析：哪些技能被频繁触发、哪些得分高却未执行。
  • 误触发排查：当技能被错误触发时，可回溯 reason 与 score 定位原因。
  • 授权审计：matched 但 denied 的记录揭示了"匹配通过但 Policy 拒绝"的情况。
匹配与授权分离：匹配不授予权限。技能被命中只表示它进入了"候选"集合， 真正执行前仍需经过 Policy 评估——检查当前 actor、project、operation 是否被允许调用该技能及其声明的工具与数据。 匹配是"能不能考虑用它"，授权是"能不能真的执行它"。
候选 ≠ 执行：技能命中只表示选择候选技能，不等于绕过 Policy 自动执行。 即使是显式触发的技能，也必须通过 Policy 评估、权限校验与预算检查后才能进入执行。 这条原则确保"用户想让 Agent 做什么"和"Agent 被允许做什么"之间始终有一层治理隔离。
CHAPTER 10

技能安装与安全

技能安装是供应链安全的关键环节。安装前必须完成哈希验证、签名验证、依赖锁校验、权限差异检查，并建立撤销机制。

10.1 安装校验清单

校验项说明失败处理
哈希验证安装包 package_hash 与 Manifest 声明一致拒绝安装
签名验证signature 用发布者公钥校验通过signature_status=invalid → quarantined
依赖锁所有 dependencies 的版本约束可满足、无冲突拒绝安装并报告冲突
权限差异检查对比已安装版本的 permissions_json权限扩张 → 视为新授权，需人工确认
撤销机制发布者可发布撤销，已安装实例自动 disabled传播撤销至所有 skill_install

10.2 权限扩张视为新授权

当新版本的 permissions_json 相比已安装版本新增了权限项（如新增了网络出口、新增了高危工具调用），系统不自动沿用旧版授权，而是将此次升级视为一次全新的授权请求：

  • 新版本进入 quarantined 状态。
  • 向用户展示权限差异（新增了什么、为什么需要）。
  • 用户显式批准后，状态流转至 enabled。

10.3 SBOM 与许可证记录

每次安装记录软件物料清单（SBOM）与许可证信息，包括：

  • 直接依赖与传递依赖的名称、版本、来源。
  • 每个组件的许可证类型（MIT / Apache-2.0 / GPL 等）。
  • 已知漏洞（CVE）关联，安装时扫描并与 SBOM 一同存档。

SBOM 使技能的供应链可追溯——当某个依赖被发现存在漏洞时，可快速定位哪些已安装技能受影响。

供应链安全：安装需哈希、签名、依赖锁、权限差异和撤销机制。 技能是可执行代码，安装即信任——任何一环缺失都可能导致恶意代码注入、权限静默扩张或供应链投毒。 Lunitide 将安装视为显式、可审计、可回滚的治理动作，而非"点击即用"的便捷操作。
CHAPTER 11

Tool 定义与授权

Tool 是技能执行时调用的原子能力（如 HTTP 请求、文件读写、代码执行）。每个 Tool 有独立的定义与授权，技能通过 permissions 声明所需 Tool，运行时由 ToolGrant 校验。

11.1 tool_definition — 工具定义

字段类型说明
idULID工具定义标识
namestring工具名称，如 http_get / file_write / code_exec
input_schema_refref输入参数 Schema 引用
output_schema_refref输出结构 Schema 引用
riskenum风险等级：low / medium / high / critical
executorref执行器引用（本地函数 / 沙箱 / 远程端点）
versionsemver工具版本

11.2 tool_grant — 工具授权

ToolGrant 记录"谁在什么范围内被允许用什么工具，以及附加约束"。授权是作用域绑定的，不是全局的。

字段类型说明
scope_typeenumworkspace / project / session

11.3 工具执行必须过 Policy 评估

即使技能已 enabled 且 ToolGrant 存在，每次工具调用仍需经过 Policy 评估。Policy 输入包括：

  • actor：发起调用的身份（用户 / 技能 / Agent）。
  • project：当前项目作用域。
  • operation：具体工具操作。
  • resource：操作目标资源。
  • normalized args：归一化后的参数。
  • data classification：涉及数据的安全分级。
  • tool trust：工具的风险等级与可信度。
  • environment：执行环境（生产 / 沙箱）。

Policy 输出 allow / deny / require_review + reason + policy_version。规则冲突时取更严格者；所有决定写入审计日志。

三层防护：Tool 风险分级（tool_definition.risk）→ 作用域授权（tool_grant）→ 运行时策略评估（Policy）。 这三层叠加确保即使技能被匹配、即使授权存在，高风险工具调用仍可在最后一刻被 Policy 拦截或要求人工审批。
