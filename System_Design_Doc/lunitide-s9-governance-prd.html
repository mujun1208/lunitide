CHAPTER 01

Policy Engine

独立风险判断

Policy Engine 是治理体系的大脑。它接受结构化输入，独立于模型与 Review Agent 做出授权决定，并产出可追溯的策略裁决。

Policy 输入

字段含义说明
actor操作发起者用户身份 / 技能身份，决定权限边界
project所属项目资源隔离粒度，限制跨项目访问
operation操作类型如 push / deploy / db_write / skill_install
resource目标资源资源句柄与版本，用于 TOCTOU 绑定
normalized args规范化参数去空格、排序、类型标准化后的参数
data classification数据分类Secret / Restricted / Internal / Public
tool trust工具信任级别内建签名 / 第三方已审核 / 未信任
environment执行环境Worker 隔离级别、网络策略、运行模式
plan version计划版本当前执行 Plan 的不可变版本号

Policy 输出

裁决语义后续动作
allow允许执行直接进入执行管线
deny拒绝执行阻断并返回 POLICY_DENIED
require_review需人工审批创建 Review，进入 pending 状态

每次裁决同时携带 reason（人类可读理由）和 policy version（策略版本号），写入审计日志。

规则冲突取更严格者。当多条策略同时命中同一操作时，裁决以最严格的策略为准 —— deny 优先于 require_review，require_review 优先于 allow。不存在"宽松策略覆盖严格策略"的路径。
模型和 Review Agent 不能修改系统强制策略。LLM 输出与 Review Agent 仅可提出 ToolCall 建议，无权变更 Policy Engine 的强制规则。来自内容的"忽略规则""自动批准"指令没有权限效果。
所有策略决定写审计。无论 allow / deny / require_review，每一次 Policy 判断都生成 AuditEvent，记录 actor、operation、裁决、reason、policy version，进入 append-only 审计链。

Policy Engine 架构要点

独立于模型

Policy Engine 是一个独立的策略裁决服务，不依赖 LLM 推理。它的输入是结构化字段，输出是确定性裁决。这保证了即使模型被 Prompt Injection 攻陷，策略边界仍然坚不可摧。

策略版本化

每条策略携带版本号。策略更新后，policy_version 递增，所有基于旧版本的 Review 批准自动失效。这确保策略变更能即时生效，不会因残留的旧批准而产生安全窗口。

裁决可解释

每次裁决携带 reason 字段，用人类可读语言说明"为什么 allow / deny / require_review"。这不仅服务于审计，也直接驱动审批 UI 向用户展示风险理由。

设计原则：最小惊讶。当 Policy Engine 无法判断时，默认返回 require_review 而非 allow。在安全系统中，不确定时选择更严格的路总是正确的。
CHAPTER 02

运行模式与自动化级别

风险分级

运行模式（Manual / Assisted / Full-Managed）只影响低风险与中风险操作的自动化程度。高风险操作无论处于何种模式，都 MUST 经过显式确认。

高风险强制确认清单

以下五类操作即使在全托管模式下也必须人工确认，不可被自动化策略绕过：

  • push、发布、生产部署 —— 任何向远端推送代码、发布产物或部署到生产环境的操作。
  • 破坏性数据库或文件操作 —— DROP、DELETE、TRUNCATE、批量删除文件、覆盖关键路径等不可逆写入。
  • 凭据导出、跨域发送敏感数据 —— 读取 / 导出 Secret 级数据，或将 Restricted 数据发送到项目隔离边界之外。
  • 执行未信任代码或扩大技能权限 —— 运行未签名 / 未审核的脚本，或提升 Skill / MCP 的权限范围。
  • 修改安全策略、审计或更新信任根 —— 变更 Policy 规则、篡改审计链、轮换签名根证书等治理元操作。
强制确认不可降级。高风险操作的设计意图是"即使全托管也不自动执行"。任何试图通过模式切换、配置覆盖或模型建议来跳过这五类确认的行为，都会被 Policy Engine 直接 deny。

三种运行模式对照

模式低风险操作中风险操作高风险操作
Manual需确认需确认需确认
Assisted自动执行需确认需确认
Full-Managed自动执行自动执行需确认（强制）

可见，从 Manual 到 Full-Managed，自动化程度递增，但高风险操作的"需确认"列在三种模式下始终一致 —— 这是治理边界的不可逾越线。

CHAPTER 03

Review 机制

不可变摘要绑定

Review 不是对"意图"的模糊批准，而是对一组不可变字段的精确绑定。批准的生效范围严格限定于审批时锁定的操作摘要。

Review 绑定字段

字段作用
operation_type操作类别，决定后续执行管线
params_hash规范化参数的哈希，任何参数变化即失效
resource目标资源标识
resource_version资源版本，防止资源在审批后被替换
plan_version计划版本，防止计划变更后沿用旧批准
policy_version策略版本，策略更新后旧批准失效
risk风险等级，用于审批 UI 展示
expires_at过期时间，超时后批准自动失效
审批只对不可变摘要生效。Review 锁定的是 params_hash + resource_version + plan_version + policy_version 的组合摘要。批准不针对"一个请求"，而是针对"这一份精确的操作快照"。
参数变化后旧批准失效。一旦 params_hash 发生变化（哪怕只改了一个参数），之前的 approved 状态立即作废，必须重新发起 Review。系统不会尝试"部分匹配"或"近似复用"。
超时默认保持暂停或拒绝，绝不自动执行。Review 到达 expires_at 后转入 expired 状态。系统不会因为"审批超时"而默认放行 —— 安全的默认值始终是"不执行"。

9 态有限自动机

Review 的生命周期由一个严格的状态机管理。每一次状态迁移都有明确的触发条件，且审批决策一旦产生即不可删除。

pending → approved / rejected / changes_requested / expired / cancelled → executing → executed / execution_failed

执行前二次校验

批准后、执行前，系统再次计算参数哈希和策略版本，并与 Review 绑定值比较：

  • 哈希一致且策略未变 → 进入 executing
  • 哈希不一致或策略已更新 → 转入 changes_requested，要求重新审批
Review 决策不可删除。approved、rejected、changes_requested 等决策记录永久保留在 append-only 审计链中。即使用户取消操作或操作执行失败，决策本身的历史不会被擦除 —— 它是治理可追溯性的基石。

状态语义说明

状态语义可迁移至
pending等待人工审批approved / rejected / changes_requested / expired / cancelled
approved已批准，待执行前二次校验executing / changes_requested（校验失败时）
rejected已拒绝，终态无（终态）

expired超时未审批，终态无（终态）
cancelled发起者主动取消，终态无（终态）

executed执行成功，终态无（终态）
execution_failed执行失败，终态无（终态，可重新发起 Review）
CHAPTER 05

审批 TOCTOU 防护

Time-of-Check vs Time-of-Use

TOCTOU（检查时与使用时不一致）是审批系统最危险的攻击面。Lunitide 通过多维绑定 + 执行前重验 + 一次性令牌来消除这一窗口。

防护层级

1. 多维不可变绑定

Review 在创建时锁定 params_hash、resource_version、plan_version、policy_version、expires_at 五个维度。任何一个维度发生变化，批准都不再有效。

2. 执行前重新读取与比较

执行前系统重新读取当前参数、资源版本、计划版本和策略版本，逐一与 Review 绑定值比较。任何一项不匹配，立即中止并转入 changes_requested。

3. 一次性 approval token

批准时生成一个 approval token，消费后立即失效。同一个 token 不可用于二次执行，防止重放攻击。

4. 并发批准互斥

当多个审批者同时操作同一 Review 时，仅第一个成功消费 token 的批准生效，其余并发批准请求返回 APPROVAL_STALE 错误。

TOCTOU 防护是审批系统的安全底线。任何绕过执行前重验、复用 approval token、或允许并发重复执行的实现，都会使整个治理体系形同虚设。这四层防护 MUST 全部实现且不可降级。
CHAPTER 06

权限与数据分类

资源级能力控制

首期虽然是单用户，仍 MUST 做资源级能力控制。Owner 身份不等于任意 Skill 自动拥有 Owner 权限 —— 最小权限原则贯穿全系统。

首期授权模型

Renderer、Host、Engine、Worker、Skill、Connector 各组件具有不同权限集。组件间调用需显式授权，不存在隐式权限继承：

  • Renderer —— 无 host object 通用反射、无文件 / shell / 网络 / secret API
  • Host —— 持有系统资源句柄，可调度 Engine 与 Worker
  • Engine —— 编排 Plan，调用模型与工具，受 Policy 约束
  • Worker —— 沙箱执行，Job Object + AppContainer 限制进程树
  • Skill —— 权限清单驱动，权限扩张视为新授权
  • Connector —— Integration 凭据隔离，按项目限定访问域

未来协作扩展引入 User、Group、Role、Permission、ProjectMembership、Session。资源 × 动作至少覆盖 project、session、memory、skill、template、base、integration、credential、task、CR、deployment、review、audit。

数据分类

级别示例默认控制
SecretAPI Key、OAuth refresh tokenOS 密钥存储；不进 DB / Renderer / 日志
Restricted源码、生产数据、附件、记忆项目隔离；外发前同意；诊断默认排除
Internal配置、计划、使用量、错误详情本地 ACL；脱敏导出
Public产品帮助、公开模板可导出共享

ConsentSnapshot 规则

云模型调用前必须生成 ConsentSnapshot。每次将数据发送到云端模型前，系统列出：供应商、模型、发送的系统提示、记忆类别、附件和工具结果范围。用户确认后才发起调用，ConsentSnapshot 写入审计。
CHAPTER 07

威胁模型与强制控制

7 类攻击面

治理体系的强度取决于最薄弱的环节。以下七类威胁面均配有强制控制措施，每一项都不可降级实现。

7.1 WebView2 / XSS 权限升级

  • WebView2 只加载打包本地受信 origin；严格 CSP，禁止 inline script / eval
  • 禁止不可信导航、新窗口和 iframe 调 Bridge
  • Bridge 校验 source、frame、schema 和白名单
  • React 禁止直接渲染未清洗 HTML；Markdown HTML 默认关闭
  • Renderer 无 host object 通用反射、文件、shell、网络和 secret API
关键控制：严格 CSP + Bridge 白名单校验。Renderer 是攻击者接触的第一个界面，必须假设其所有输入均被污染。CSP 与 Bridge 双重校验确保 XSS 无法升级为本地权限调用。

7.2 Prompt Injection

上传文件、网页、模型输出、MCP / 接口数据必须标记 untrusted_content。模型文本只可提出 ToolCall，Policy Engine 基于结构化参数独立授权。来自内容的"忽略规则""自动批准"没有权限效果。

关键控制：untrusted_content 标记 + Policy 独立授权。模型永远不能直接执行副作用操作。Prompt Injection 的危害止步于"建议"，因为授权决定权在 Policy Engine 而非模型。

7.3 工具、文件与 Worker 隔离

  • 路径先 canonicalize 再授权；阻止 ..、UNC、ADS、junction / symlink 逃逸
  • 文件写入限定项目根及明确授权目录
  • 命令使用 executable + argv，不拼接 shell 字符串
  • Worker 使用 Windows Job Object 限制进程树、CPU、内存和时间，另需 AppContainer 或低完整性 Restricted Token、staging ACL、网络默认拒绝和 capability token
  • 环境变量白名单；secret 按单次调用最小化注入
  • 输出大小有限，超限截断并保存安全引用

Worker 安全 POC 必须验证：读取 %USERPROFILE% 被拒、未授权局域网访问被拒、子进程逃逸失败、Named Pipe 探测失败、junction / ADS 逃逸失败。若任一项无法满足，v1 继续只允许签名内建工具。

关键控制：句柄级路径授权 + Job Object + 条件性 OS 隔离。Job Object 仅限制生命周期和资源，绝不是完整安全沙箱；canonicalize 也不能单独消除 junction/reparse-point TOCTOU。M0/M1 只运行随产品发布、签名且 manifest 固定的内建工具。只有 AppContainer/低完整性 POC 全部通过并由独立 ADR 批准后，才可声称开放受限第三方执行；不得承诺“被攻破后绝对无法逃逸”。文件读写必须逐级以句柄打开并校验最终 file identity、volume、祖先根和 reparse point，检查与 open/rename/delete 绑定同一父目录句柄。

7.4 Skill / MCP 供应链

  • 包、manifest、依赖锁必须 hash；生产源应签名
  • 安装展示权限清单；权限扩张视为新授权
  • 支持撤销列表、quarantine、回滚
  • M0/M1 第三方 stdio server 一律不可运行；可导入、校验并显示为 quarantined。未来隔离 ADR 批准后，未信任 server 仍不得启动
  • SBOM 和许可证记录必须保留
关键控制：hash + 签名 + 权限清单 + quarantine。第三方技能是供应链攻击的主要入口。每个技能的安装、升级、权限变更都必须经过显式审核与可验证的完整性校验。

7.5 文件解析攻击

检查 MIME 与魔数；限制大小、页数、压缩比、嵌套深度；防 zip bomb 和路径穿越；禁用 Office 宏；HTML 清洗主动内容；高风险解析器在 Worker 运行。

关键控制：MIME 魔数双校验 + 大小/压缩比限制 + Worker 隔离解析。解析器是内存破坏漏洞的高发区。将高风险解析器放入 Worker 隔离执行，即使被攻破也无法影响宿主。

7.6 更新供应链

安装器、二进制和更新 manifest 必须 Authenticode / 独立签名与 SHA-256 验证；防降级、防重放；记录最低允许版本；证书轮换需双签过渡；构建生成 SBOM 和制品证明。

关键控制：Authenticode 签名 + 防降级 + SBOM。更新通道被劫持可导致整个系统被替换。签名验证与版本下限确保只接受可信且不低于安全基线的更新。

7.7 审批 TOCTOU

Review 绑定 params_hash、resource_version、plan_version、policy_version、expires_at。执行前重新读取并比较；一次性 approval token 消费后失效；并发批准仅一个成功。

关键控制：多维绑定 + 执行前重验 + 一次性 token。详见 第 5 章。TOCTOU 是审批系统最危险的窗口，必须用多层防护完全闭合。
CHAPTER 08

审计系统

append-only · hash chain

审计是治理可追溯性的最后防线。所有安全相关操作 MUST 写入 append-only 审计链，每条记录与前一条哈希链接，用户可独立验证完整性。

必须审计的操作

  • 策略判断（Policy 裁决）
  • 审批（Review 创建 / 决策）
  • 密钥新增 / 替换 / 删除
  • 技能安装 / 升级 / 卸载
  • 工具副作用（文件写入 / 命令执行）
  • 接口测试（Integration 调用）
  • 任务状态变更
  • CR 审批
  • 部署
  • 更新（版本变更）
  • 备份恢复

审计链完整性

append-only + tamper-evident hash chain。每个 Workspace 使用一条明确 chain_id 的串行链；Engine 单写者在同一事务中分配单调 audit_seq，并以版本化 canonical encoding 计算 event_hash。唯一约束 (chain_id, audit_seq) 防止并发分叉。该本地链能检测部分损坏/非同步篡改，但不能声称抵御可重写整个 DB 的同用户攻击者。
用户可验证完整性。系统提供校验工具、genesis/epoch、链头与截断检测；发布和审计导出前强制验链。需要更强证据时，以 DPAPI/TPM 保护的签名密钥定期签链头，或锚定到独立位置。安全审计独立保留；业务内容删除后只保留最小、不可逆摘要和墓碑，不保留原文。

禁止记录的内容

日志脱敏是不可妥协的红线。以下内容严禁出现在任何日志中：
  • secret —— API Key、OAuth token、密码等凭据
  • Authorization —— 认证头、Bearer token
  • 完整提示词 —— 发送给模型的 system / user prompt 全文
  • 附件正文 —— 上传文件的原始内容
  • 未脱敏 URL —— 含 token 或敏感参数的 URL

日志保留策略

默认保留 14 天或 200MB，先到者清理。日志级别可配置。安全审计独立保留，不受普通日志清理策略影响，不能被普通日志清理删除。

全链路 Trace

用户动作 → Bridge → Engine → 模型 / 工具 → 存储，全链路共享同一个 traceId。模型调用记录 provider / model、阶段、耗时、token、结果码，但不记录 Key。

CHAPTER 10

诊断包

安全导出 · 内容清单

诊断包用于排障上报。它默认排除所有敏感数据，导出前向用户展示完整内容清单，确保用户明确知道将要分享什么。

默认包含

  • 版本 —— 应用版本号
  • OS / WebView2 版本 —— 操作系统与运行时版本
  • 组件健康 —— 各组件状态
  • 脱敏日志 —— 经过脱敏处理的近期日志
  • DB schema / migration 状态 —— 数据库结构与迁移记录
  • 配置摘要 —— 非敏感配置项
  • 近期错误 —— 错误码与堆栈（脱敏）
  • 校验结果 —— 审计链完整性校验结果

默认排除

  • Key —— 所有密钥与凭据
  • prompt —— 完整提示词
  • 源码 —— 项目源代码
  • 附件 —— 上传文件正文
  • 记忆正文 —— Memory 存储内容
导出前展示内容清单。诊断包在生成后、分享前，系统向用户展示完整的文件列表与字段摘要。用户确认后才能导出或分享，杜绝"静默泄露"。

NORMATIVE ADDENDUM

协作冲突与发布治理裁决

MUST
并发模型：禁止长期悲观代码锁与 last-write-wins。编辑阶段显示 Presence 和对象/路径/符号/迁移重叠预警；保存与提交必须携带 base_hash + base_version，通过 CAS 与 Git 三方合并解决，冲突返回 stale/merge_required，不得静默覆盖。
治理对象状态 / 约束审计要求
ChangeTaskdraft → active → submitted → merged；冲突 merge_required；取消 cancelled记录参与者、base/current/merged hash、冲突和解决人
CRRevisionassembling → submitted → approved → frozen；漂移 changed_after_approval 并新建修订记录 manifest、审批 hash、证据与决策
ReleasePackage不可变；绑定代码、DatabaseContract、MigrationPackage、IntegrationVersion、证据、回退方案记录 digest、冻结短租约及每次校验
Promotionpending → gated → preflight → importing → verifying → succeeded；可转 blocked / failed / rollback_required / outcome_unknown同 digest 按 development→test（可选）→production；记录门禁和实际结果
Leaseactive → expired / released / revoked；仅 package_freeze / target_environment_import，TTL + fencing token记录获取、续租、过期、拒绝和 token 摘要
ReleaseRunpreflight → restore_point → migrating → post_scan → deploying → verifying → succeeded逐阶段记录输入/输出 digest、错误、补偿与操作者

固定 transport 为 ChangeTask → CR Revision → ReleasePackage → Promotion。开发本地生效不算传输；development + production 为 1 次晋级，development + test + production 为 2 次晋级。仅 ReleasePackage 冻结和目标环境导入可使用 TTL 短租约；不得扩展到代码编辑或人工等待。

环境门禁：development 验证成功才可晋级；配置 test 时不得跳过，须测试、契约与证据通过后进入 production；生产还要求职责分离、有效生产批准、维护窗和恢复点能力。每次晋级重验同一 package digest 与审批摘要。

代码 + 数据库同包执行门禁

固定编排为：preflight 只读契约检查 → 恢复点 → 执行已批准 MigrationPackage（external / project_tool / controlled MigrationAdapter）→ 迁移后重扫 → 部署代码 → 健康 + 契约复核。数据库与代码不得无序同时并行；失败即停止，未知结果进入 outcome_unknown，先对账再重试。

Expand–Migrate–Contract：Expand 建立兼容结构，Migrate 回填并部署兼容代码，破坏性 Contract 必须在后续独立 ReleasePackage 执行，不得与 Expand 同次自动执行。无 MigrationAdapter 时 DB 变更是 external prerequisite，须以外部证据、实际 schema digest 和 post-check 放行。

审批摘要：覆盖 revision manifest、package/code digest、DatabaseContract、MigrationPackage、IntegrationVersion、证据、回退方案、目标环境、promotion path、破坏性标记与 policy version；UI 展示风险、职责分离、迁移步骤和恢复策略，冻结及每次晋级前重算。

失败与审计：迁移成功而代码失败时数据库不默认逆迁移；复核失败将环境标记 degraded 并阻断晋级。冲突、三方合并、Presence/重叠预警、状态迁移、租约、审批摘要、门禁、迁移输出、部署、失败、补偿和回退均写 append-only AuditEvent。
