开发就绪标准与开工裁决

本页把《PRD提示词模板_Lunitide.md》的工程机制固化为 V2.0 的开发就绪（Dev-Ready）标准 v1.0，记录 M0–M4 完成口径与 M5 开工裁决，并给出开发人员第 0 天起的傻瓜式执行流程。M5–M9 各阶段五件套按本标准补齐后即为「可直接拿着去开发」的 PRD。

模板评估合理性与适配裁决Dev-Ready 标准六件套格式规范开工裁决M0–M4 口径与 M5 开工达标落点M5–M9 六件套位置第 0 天流程假设验证与任务卡执行设计变更规则代码为准与回写

1. 提示词模板评估与适配裁决

评估对象：《AI 生成可落地 PRD 的完整提示词模板（Lunitide 版）》（两阶段生成 + 设计假设清单 + 任务卡拆解 + 错误矩阵）。总体结论：模板合理，工程质量高，予以采纳；它精确命中了「开发可直接照着写代码」的四个断点（任务粒度、契约粒度、假设显性化、错误穷举），与 V2.0 已有的治理体系（状态机、门禁、灰度回滚、追踪矩阵）互补而不冲突。

模板机制防什么评估裁决
两阶段生成（先理解报告再写 PRD）AI 没读懂代码就动笔合理；对已存在五件套的场景，阶段一理解报告由 M0–M4 代码现实替代转化为「设计假设清单 + 第 0 天验证」（见 §2.6）
理解报告必须注明出处行号凭印象编造签名合理并入假设清单的验证命令列（grep/读文件）
设计假设清单（A-001 + 验证方式）错误假设被带进开发合理，是本页核心采纳项全盘采纳：每阶段 02-技术设计 落「设计假设清单」，第 0 天逐条签字
任务卡（半天粒度 + 文件 + DoD + 验证命令）切片太粗，开发仍需自己做设计决策合理，是「无脑开发」的第一断点全盘采纳：每阶段 05-实施顺序 落「任务卡总表」
错误矩阵（方法 × 6 类错误逐格）凑数编造、漏致命场景合理全盘采纳：每阶段 04-测试与验收 落「错误矩阵」，N/A 必须写原因
UI/交互规格（组件树 + 四态 + Bridge 调用时机）前端不知道界面怎么做合理；V2.0 的 03/06 已有八态与页面契约，覆盖更强以 V2.0 现有页面契约为准；四态作为最低检查线并入 04 验收
性能 P50<100ms / P99<500ms 式指标「系统应有较好性能」式废话方向合理；但 V2.0 存量指标统一为 P95 口径，全量改 P50/P99 会制造两套口径统一口径：常规方法 P95，关键路径方法补 P99（见 §2.7）；禁止无指标的方法进入任务卡
设计变更规则（代码为准 + 回写 PRD）悄悄偏离，文档腐烂合理，与 00 治理变更流程同向合并进本页 §6，按 00 治理执行
五项适配修正（模板 → V2.0）：① 单模块粒度 → 里程碑级：任务卡落在各阶段 05；② 两阶段生成 → 假设清单机制（文档已存在，理解验证后置到开发第 0 天）；③ P50/P99 → P95 为主、关键路径补 P99；④ 模板未覆盖的治理机制（ADR、状态机 guard、灰度、回滚、迁移门禁、Scope Seal）继续以 V2.0 现有规则为准；⑤ 模板约束条件（不引入 Python/Node 运行时、schema 生成 TS 类型、不改已应用 migration、中文错误消息）与 V2.0 一致，原样生效。

2. Dev-Ready 标准 v1.0（六件套）

一个里程碑「可直接开发」当且仅当以下六件套全部落盘。任何一件缺失，对应任务卡不得开工；发现缺失时先补文档（走 00 治理变更流程），再开发。

#件格式规范（强制）落点
1FR 规范化每条功能需求有编号 + 优先级（P0 发布阻断 / P1 首期必须 / P2 可延期）；P0 级 FR 必须写明输入 / 输出 / 处理逻辑 / 异常处理四段；禁止「系统应支持 XX」式无行为描述各阶段 01-阶段PRD（存量 FR 表补优先级映射，新增 FR 直接按四段写）
2Bridge JSON Schema每个新增 Bridge/RPC 方法给出每方法独立 request/success/error 三个 JSON Schema（字段名、类型、required、枚举、additionalProperties=false；error 引用全局 AppError v1）；schema 文件入库 bridge/schema/*.json 并生成 TypeScript 类型，禁止手写 TS 类型；schema 版本号写入变更记录各阶段 02-技术设计
3SQLite DDL新增/修改表给出列名、类型、NOT NULL、DEFAULT、索引、外键；新变更必须新 migration，禁止修改已应用 migration；migration 命名 NNNN_描述.sql，起编号以第 0 天核对的当前最大编号为准（假设清单 A-001）各阶段 02-技术设计
4错误矩阵「每个新增方法 × 六类错误（参数非法 / 审批拒绝 / 依赖故障 / 资源不足 / 取消与超时 / 并发冲突）」逐格填写，不适用写 N/A + 原因；汇总错误码表：码、用户可见中文消息、是否可重试、是否记审计各阶段 04-测试与验收
5任务卡半天–一天粒度；列：任务编号 / 文件路径 / 改动描述 / 完成定义 DoD / 验证命令 / 依赖任务；DoD 必须可客观验证（编译通过、某测试全绿、某命令输出符合预期），禁止「功能正常」各阶段 05-实施顺序（任务卡总表，切片内有序）
6设计假设清单对本 PRD 引用的现有签名 / 表结构 / 配置 / 错误码逐条编号（A-001…），列：假设内容 / 验证方式（grep 命令或检查方法）/ 验证结果（第 0 天填写）；宁可多写不可漏写各阶段 02-技术设计（开发第 0 天在该表签字）

2.7 非功能指标口径

方法类别延迟口径最低要求
同步读（查询/读取/列表）P95≤ 100ms（本地 SQLite/内存）；跨进程 ≤ 200ms
同步写（创建/更新/提交）P95≤ 300ms（不含下游模型调用）
关键路径（流式首事件、取消、回滚）P95 + P99沿用各阶段冻结参数表数值；P99 ≤ 2×P95
长任务（构建/迁移/发布）不设延迟，设吞吐与超时必须支持取消（context 传递）与进度事件；超时上限沿用冻结参数

3. M0–M4 完成口径与 M5 开工裁决

裁决记录（2026-08-14，用户决策）：M0–M4 主体开发视为已完成，M5 即刻开工。依据 00 治理优先级链第 1 级（用户决策与已接受 ADR 最高），本裁决覆盖「M4 Scope Seal 未完成阻断 M5 执行核复用」的原口径：Scope Seal 与 M0–M4 正式外验残留不再作为 M5 开发开工的阻断项，转为在 M5 实施期间并行补齐，并保留为 M5 对外发布门禁的前置条件。状态必须拆分：M0–M4 主体代码按用户裁决视同实现基线；内部验证仍需逐证据核对，不得批量关闭；M4 Scope Seal 并行补齐；正式外验独立未关闭，不得表述为「已外验/已上线」。

5. 开发者执行流程（第 0 天起，傻瓜式）

  1. 读两页：本页 + 所在阶段 05-实施顺序（任务卡总表）。开发顺序固定：M5 → M6 → M7 → M8 → M9（M9 需 ADR-011 解除）。
  2. 第 0 天验证假设：打开所在阶段 02-技术设计 的「设计假设清单」，逐条执行验证命令（grep / 读文件 / 跑命令），在「验证结果」列填写 ✓/✗ 与实际值；全部 ✓ 后在表尾签字（姓名 + 日期）方可领任务卡。
  3. 出现 ✗：立即停止，按 §6 设计变更规则回写 PRD（标注「已修订 + 日期 + 原因」），等待文档更新后重新验证；禁止带着错误假设开发。
  4. 领任务卡：按 05 任务卡总表顺序领取（依赖列全部完成的卡才可领）；每卡半天–一天。
  5. 执行每张卡：改「文件路径」列指定的文件 → 跑「验证命令」→ 输出满足「DoD」即完成；DoD 不可客观验证时视为任务卡不合格，回写文档。
  6. 设计冲突：立即停卡并分类。仅不改变行为合同的路径/签名漂移可按代码现实修正文档；涉及产品行为、生产栈、schema、状态机、安全、权限、阶段边界或验收时，权威设计优先，修正实现或走 ADR，禁止用现有原型反向改写设计。
  7. 提交：任务卡完成 + 对应阶段错误矩阵中该方法的格子全部有测试覆盖 → 提交代码与验证命令输出（作为完成证据）。
