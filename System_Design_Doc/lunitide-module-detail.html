CHAPTER 01

模板管理模块

实体 tpl_template / tpl_version / tpl_usage

模板是产物生成的格式契约。模块负责模板的草稿、启用、停用与作废全生命周期，以及版本的发布与弃用，确保产物可追溯、可重现。

1.1 模板状态机

模板主记录的顶层状态控制其是否可被引用：

draft
草稿
→
enabled
已启用
→
disabled
已停用
→
void
已作废
void 后禁止新引用，但历史引用仍可基于已锁定的 template_version_id 完整重现。

1.2 模板版本状态

版本状态独立于模板主状态，用于细粒度版本治理：

draft
版本草稿
→
published
已发布
→
deprecated
已弃用

1.3 业务规则

  • 上传默认保存草稿，不"上传即启用"——新模板必须经过显式启用才能进入引用链。
  • 同一 report_type 同一 scope 最多一个默认模板，由部分唯一索引强制约束。
  • 未配置、未选择或解析失败时 MUST 使用内建默认模板生成，保证链路不中断。
  • 产物记录确切的 template_version_id，而非模板主 ID——确保历史产物可精确重现。
  • 已被引用的模板 / 版本 禁止物理删除，只允许逻辑作废。
  • void 后禁止新引用，但历史引用可重现。
DDL · tpl_template / tpl_version / tpl_usage

索引定义语义
ux_tpl_defaultUNIQUE(report_type, scope_type, COALESCE(scope_id,'')) WHERE is_default=1 AND status='enabled'部分唯一索引，保证每个 report_type × scope 至多一个启用的默认模板；scope_id 为 NULL 时以空串参与比较

CHAPTER 02

底座复用模块

实体 BaseAsset / BaseVersion / BaseRef

底座是跨项目共享的可复用资产单元。项目通过 BaseRef 锁定具体版本，业务 overlay 与底座内容分离，确保上游演进不静默破坏下游。

2.1 底座种类

UI Base
组件库、主题、布局模板、设计令牌。项目引用锁定版本后，业务侧仅以 overlay 注入差异。
Database Base
共享 schema、迁移脚本、种子数据。版本化与 schema 演进绑定，breaking 变更需显式确认。
Common Code
跨项目通用代码包：工具函数、SDK、协议定义。以 semver + package_hash 锁定。

2.2 版本锁定机制

项目通过 BaseRef 锁定具体版本，不是浮动范围引用。BaseRef 必须保存以下字段：

  • locked_version_id — 锁定的 BaseVersion 主键，决定项目实际使用的底座内容。
  • overlay_ref — 项目侧覆盖内容引用，与底座内容物理分离。
  • compatibility_status — 当前锁定版本相对最新版本的兼容状态。
  • last_checked_at — 上次检查上游新版本的时间戳。
上游发布新版本不得静默影响项目。新版本仅更新 BaseVersion 表与兼容性提示；项目实际使用的底座内容由 BaseRef.locked_version_id 决定，必须由项目显式升级动作才能变更。

2.3 overlay 分离机制

底座内容与业务 overlay 分离存储。合并发生在构建/渲染期，而非存储期：

BaseVersion
底座内容
+
Overlay
业务覆盖
→
合并产物
build-time

这一分离保证了底座可独立升级、overlay 可独立演进，二者解耦。

2.4 breaking 升级规则

breaking 升级 MUST 展示差异和兼容性报告并显式确认。系统不得自动将项目从 v1 升级到 v2-breaking；必须呈现 breaking change 列表、受影响 overlay 项、迁移建议，并由有权限的角色显式批准。

3.5 约束规则

  • 每个 Provider 最多一个 enabled default model——由部分唯一索引约束。
  • UNIQUE(provider_id, model_id)——同一 Provider 下模型标识唯一。
  • 协议或主机变化 触发 credential origin 再确认：origin_fingerprint 不匹配时，旧凭据引用视为需重新授权。
  • 健康状态不得只依赖最后一次结果，应由滑动窗口计算。

3.7 Key 安全规则

API Key 永不回显。凭据仅存引用（credential_ref），不存明文；任何接口返回、日志、审计事件中均不得出现密钥原文。ChatRequest 不得携带 API Key，密钥由网关在出口侧注入。

4.3 关键约束说明

  • root_path 授权前必须规范化——防止路径穿越、符号链接逃逸与大小写歧义。
  • attachment 解析隔离——附件解析在沙箱内进行，parse_status 独立追踪，失败不阻断会话主流程。
  • message sequence 严格递增——UNIQUE(session_id, sequence) 保证消息有序且可回放。
  • message_part ordinal 唯一——同一消息内多模态片段有序且不重复。
  • 单会话逻辑上下文至少 1M tokens——logical_tokens 是累计可重建容量，不受模型单次窗口或消息分页上限约束。
  • 消息原文与摘要分离——压缩只追加 context_summary；不得 UPDATE/DELETE 源 message。显式数据删除是唯一例外，并通过墓碑使派生摘要和 Handoff 失效。
  • 摘要保真合同——每个事实性、状态性、决策性、约束性、任务性和证据性 claim 必须关联叶级 Message/ToolResult/Artifact revision；建议/推断显式标型并保存 derivation sources，仅指向父摘要不算完成溯源。
  • 分页不是容量限制——消息 RPC 使用 sequence cursor 向前/向后分页；单页最大 200 条和 payload 上限不得写入 session 总量校验。

Planning 负责将目标分解为可执行的 DAG，Governance 负责策略评估、审批门控与不可篡改的审计链。二者共同保证"自治可追溯、高风险必确认"。

Planner / Orchestrator 规则

  • Planner 输出 DAG 及 graph hash，保存为 PlanVersion；graph_hash 用于检测计划被篡改。
  • Orchestrator 只调度依赖满足、策略允许、预算充足的节点。
  • 预算包括：最大模型调用、tokens、费用、墙钟时间、工具调用数、并行数。
  • 每个副作用节点必须有 idempotency key、风险等级和可验证完成条件。
  • 反思不得无限循环；达到重试/预算上限后熔断并请求人工决定。

6.2 治理实体

实体关键字段
policyid, scope, version, status, rules_ref

Policy 与 Review 规则

  • Policy 输入：actor、project、operation、resource、normalized args、data classification、tool trust、environment、plan version。
  • Policy 输出：allow / deny / require_review + reason + policy version。
  • 规则冲突取更严格者；模型和 Review Agent 不能修改系统强制策略。
  • Review 绑定操作类型、规范化参数哈希、目标资源、计划版本、策略版本、风险、过期时间。参数变化后旧批准失效。
  • 超时默认保持暂停或拒绝，绝不自动执行。

6.3 审计事件：append-only + hash chain

audit_event 是系统治理的最终证据层，采用追加写与哈希链双重保护：

event_1
prev_hash=∅
→
event_2
prev_hash=h1
→
event_3
prev_hash=h2
→
event_N
prev_hash=h(N-1)
审计事件 append-only + tamper-evident hash chain。权威算法见治理 PRD：每个 Workspace 使用 chain_id + 单调 audit_seq，Engine 单写者串行追加并计算版本化 canonical event_hash。普通链可检测中间记录篡改/删除，但不能单独检测完整链尾截断或整库回滚；周期性签名 checkpoint 必须包含 workspace_id、epoch、last_sequence、head_hash、timestamp，并保存在业务备份之外的受保护位置。恢复时若备份 head 落后于已知最高 checkpoint，进入 audit_rollback_detected / recovery_required，禁止宣称链完整。

7.3 索引约束

  • (project_id, node_type, natural_key) 唯一——同一项目内同类节点的自然键唯一，防止重复解析产生重复节点。
  • Edge：(project_id, from_id, edge_type) 索引——支撑从源节点出发的邻接遍历。
  • 所有查询强制 project_id——本体查询不可跨项目，从数据层杜绝越权读取。
  • 向量记录必须带 workspace/project scope、source revision 和 tombstone。

7.4 解析与增量索引

Ontology Engine 职责链：源快照 → 解析 → 节点边 → 版本化索引 → 查询。增量索引按内容哈希驱动；单文件失败不阻断其他文件。查询返回来源与 revision，保证可追溯。Markdown / JSON / Go / TS 是候选 POC 范围，最终首期范围以 ADR-006 批准结果为准；其他语言通过 parser registry 扩展。

CHAPTER 08

Memory 实体

Memory Manager 是系统的记忆中枢。记忆按四层分级管理，每条记忆带来源、作用域、可信度、重要度与修订记录，召回综合多维评分并返回解释。

8.2 四层统一

working
当前 run 的临时状态，生命周期最短，run 结束即清理。
short_term
会话级摘要，跨单轮但限于会话范围。
long_term
用户确认的事实、偏好、决策、情节。情节记忆作为 kind=episodic 的长期记忆，而非第五层。
semantic
由本体或事实结构化出的知识，与 Ontology 节点联动。

8.3 写入与召回规则

  • 每条记忆必须有来源、作用域、可信度、重要度和修订记录。
  • 模型推断不能自动升级成"已确认事实"——必须经用户显式确认。
  • 召回综合相关度、时效、重要度和可信度，并返回解释（为何召回这条）。
  • 删除需传播至结构化记录、向量、缓存和摘要——deletion_tombstone 驱动多存储一致性。

8.4 隔离红线

跨项目泄漏率必须为 0。记忆以 project_id 强作用域，查询层与存储层双重强制；任何召回路径不得返回非当前 project 的记忆。向量索引同样带 workspace/project scope，删除需传播 tombstone。
