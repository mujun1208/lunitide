关键算法

显式晋升

confirmation_token 绑定 candidate_id、payload_digest、actor、scope 与过期时间；事务内创建 Fact、全部 SourceLeaf 和审计。置信度、频次、压缩均不能代替 token。

Recall

先做主体/空间过滤，再混合检索与重排；解释输出命中因子、来源、新鲜度和裁剪。受限结果不暴露名称、数量或摘要。

递归墓碑

先在读面立即隐藏，再按依赖图和可恢复游标清索引、缓存、摘要、Handoff、运行输入及设备副本；收齐 ACK 后压缩。备份恢复必须先重放墓碑水位。

同步冲突

版本向量检测并发。不同 JSON 叶自动合并；同叶创建 SyncConflict。删除与编辑冲突默认保持不可见，待人工处理。

隔离、安全与可观测性

  • subject_id + scope_id 强制行过滤；索引命名空间、缓存键、对象前缀均包含隔离域。
  • 传输与静态加密；按主体/空间封装密钥；吊销后不可恢复。
  • 审计确认、召回、导出、删除、交接、Bundle 启停和恢复，不记录敏感原文。
  • 恢复先加载密钥吊销和墓碑，再重放 Outbox、重建投影、校验同步水位，禁止删除对象回活。

Provenance Adapter 与消费契约

ProvenanceAdapter 是 M7 产物进入 M8 的唯一入口：校验 artifact_id/version、不可变摘要、来源链、gate_passed_at、freshness/stale 状态与当前授权快照；任一缺失、过期、stale 或权限撤回均 fail closed。聊天正文与未过门禁草稿只能生成隔离候选，不得成为事实源。

Adapter 维护 M7 产物→候选→事实→索引/缓存/摘要/Handoff/自动化输入的派生边；上游撤回、授权撤销或删除产生版本化 tombstone，经 Outbox 传播并要求每个投影 ACK。删除传播未 verified 前读面持续不可见，恢复必须先重放墓碑水位。

Ontology 管线与 legacy 迁移技术设计

Snapshot → Parse → Graph → Versioned Index → Query

Authorized Source
  → Snapshot(scope_id, revision, content_hash, captured_at)
  → Parse(file isolation, line spans, parser version)
  → Graph(nodes, edges, provenance)
  → Versioned Index(index_version, graph_version, atomic alias)
  → Query(scope gate, version pin, provenance response)
阶段输入/输出不变量与失败处理
Snapshot输入文件/文档 revision；输出不可变 snapshot 与逐内容块 SHA-256subject_id + scope_id 是复合隔离键；同哈希跳过重解析，变更仅重算受影响子图。
Parsesnapshot → ParseResult/ParseFailure每文件独立事务与资源配额；失败写 quarantine、错误摘要和 parser_version，不发布部分结果，不阻塞其他文件。
GraphParseResult → EntityNode + RelationEdge节点类型封闭为 File、Document、Artifact、Requirement、Decision、Module、Class、Function、Interface、Table、Field、UseCase、TestCase、Task、Release；边必须有 from/to、relation_type 与 provenance。
Versioned Indexgraph_version → immutable index_version构建、校验后原子切换 scope 内别名；失败保留上一可用版本；版本不可原地覆盖。
Queryquery + scope + index_version → nodes/edges先授权与 scope 过滤再检索；响应携带命中版本、source locator 与 revision，不泄露其他 scope 的存在性。

图实体、来源与增量

EntityNode(node_id, node_type, canonical_key, properties, scope_id, snapshot_id, content_hash, deleted_at) 表示实体/节点；RelationEdge(edge_id, from_node_id, to_node_id, relation_type, scope_id, snapshot_id, content_hash, deleted_at) 表示边。二者均绑定 Provenance(source_ref, line_start, line_end, revision, snapshot_id, parser_version)；文件行范围为闭区间且必须校验边界。

增量规划器比较 source revision 与内容哈希：未变复用既有子图；新增 upsert；变更先生成新版本节点/边再原子发布；删除写 tombstone。墓碑沿 source→snapshot→node/edge→index document→query cache 传播并逐投影 ACK，读面从墓碑创建起立即隐藏。恢复、重建或延迟事件消费均先加载墓碑水位，禁止删除对象回活。

写入分级与必备属性（V1 基线）

Memory Manager 在写入时必须为每条记忆标注来源、作用域、可信度、重要度与修订记录，写入门槛随层级递进升高：

层级写入门槛典型内容可信度来源
working无门槛，run 内自动写入中间变量、工具暂存结果不标注，run 结束清理
short_term会话内自动摘要近期交互片段、会话摘要模型生成，标注低可信度
long_term需用户确认事实、偏好、决策、情节用户确认 = 1.0
semantic本体校验 + 结构化知识图谱节点、关系本体权威性决定
  • 来源（source）：必须可追溯到 user_message / tool_output / model_inference / import 之一，记录 quote_ref 原文引用。
  • 作用域（scope）：workspace_id + project_id 双重隔离，决定可见范围与召回边界（新版为 subject_id + scope_id）。
  • 可信度（confidence）：[0,1] 浮点，用户确认 = 1.0，模型推断 < 1.0，影响召回权重。
  • 重要度（importance）：[0,1] 浮点，由内容性质与用户行为信号综合评估。
  • 修订记录（revision）：每次修订生成 memory_revision，记录 old_ref / new_ref / reason / actor。

召回四维（评分因子与组合规则）

V1 召回综合评分由四个维度加权融合，每个维度直接来自记忆条目元数据：

因素权重维度说明
相关度语义相似 + 关键词命中向量相似度与词项匹配的加权融合
时效时间衰减越近期的记忆权重越高，长期记忆衰减更慢
重要度importance 字段写入时标注的重要度直接参与评分
可信度confidence 字段用户确认的记忆优先于模型推断

返回解释：每次召回不仅返回记忆内容，还返回为什么召回这条记忆的解释——包括命中的因素、得分构成与来源引用（quote_ref）。解释能力让召回过程可审计、可调试，也支撑 UI 上的「记忆溯源」展示。

召回日志用途：每次召回写入一条 recall_event（session_id、query_hash、memory_id、score、rank、injected_tokens、time），用于：

  • 召回质量分析：统计命中率、排序合理性、低质量召回占比。
  • 上下文预算管理：追踪 injected_tokens 累积，防止记忆注入挤占模型上下文。
  • 召回链路审计：回答「这条记忆是在什么会话、什么查询下被召回的」。

injected_tokens 注入限制：召回的记忆会被注入到模型上下文中，但注入量受 injected_tokens 上限约束。当召回结果超出预算时，按 rank 裁剪低分记忆，确保不挤压用户当前输入与系统指令的空间。

技能生命周期状态机（七状态）

技能从草稿到卸载经历七个状态，每个状态转换都有明确的触发条件与校验要求，确保生命周期可控、可审计：

状态含义是否可执行
draft草稿，Manifest 编辑中，未校验否
validated已通过 Manifest 完整性与签名校验否
installed已安装到工作空间，尚未启用否
enabled已启用，可被匹配与触发是
disabled已禁用，暂停触发但保留安装否
quarantined隔离，因安全风险暂停，需人工审查否
uninstalled已卸载，安装记录归档否

正常路径单向递进：draft → validated → installed → enabled ⇄ disabled → uninstalled；安全路径：installed/enabled → quarantined → uninstalled。隔离触发条件：当一个新版本的 signature_status 为 invalid，或其 permissions_json 相比已安装版本出现权限扩张时，系统不自动启用，而是将其置入隔离态，等待人工审查与显式授权——这防止「静默提权」，即技能通过版本升级悄悄获取更高权限。

新版承接：M8 WorkflowBundle（draft→validated→enabled/disabled/quarantined，含 checksum、permissions、rollback_ref）与 M6 第三方导入治理（discovered→pinned→inspected→scanned→evaluated→awaiting_approval→approved|rejected|revoked，导入不等于安装或启用）沿用同一生命周期骨架；本节七状态表是两者的字段级演进基线。

技能中心页面信息架构（V1 UI 原型基线）

  • 布局：「列表 + 详情」双栏。列表用状态色点一眼区分技能健康度（绿 = enabled / 黄 = disabled / 红 = quarantined），显示技能名与版本号；工作空间头部显示已安装数量、enabled / quarantined 统计，并提供「安装技能」「触发日志」入口。
