Lunitide 是个人本地优先、BYOK 的 AI 软件生命周期工作台。用户把 "想法 → 需求 → 架构 → 设计 → 开发 → 测试 → 部署" 持续交给一个理解项目语义、 记得历史、可扩展、能规划且有治理边界的 AI 开发伙伴。

本地优先含义：配置、项目、会话和密钥默认本机持有；使用云模型时，提示词、选定上下文和附件会发送给所选供应商。系统 MUST 在发送前展示数据边界，不承诺"数据完全不出本机"。

CHAPTER 01

产品愿景、目标与边界

1.1 愿景

让用户把"想法 → 需求 → 架构 → 设计 → 开发 → 测试 → 部署"持续交给一个 理解项目语义、记得历史、可扩展、能规划且有治理边界的 AI 开发伙伴。

规范词：MUST / 必须为编码与验收不可省略项；MUST NOT / 禁止违反即阻断合并或发布；SHOULD / 应当原则上实现，任何偏离必须提交 ADR；MAY / 可以按里程碑选择。Open / Deferred ADR 未批准前不得由实现者自行固化或扩展范围。

1.2 核心价值

连续理解

跨会话记住已确认事实、决策和偏好，不因重启或断线丢失上下文。

语义一致

所有专家共享项目本体和版本化产物，避免口径分裂。

计划执行

复杂任务转为可恢复 DAG，不靠单轮提示词硬跑。

可控自动化

低风险自动，高风险强制确认并留痕，运行模式仅影响中低风险程度。

资产复用

模板、底座、技能和接口配置可版本化复用，引用锁定不可静默变更。

本地控制

用户掌握密钥、项目存储、外发范围和删除权。

1.3 首期产品边界

首期 MUST 承诺

  • 单用户 Windows 本地工作台
  • 多供应商、多模型 BYOK
  • 项目、会话、九阶段、产物与版本基础模型
  • 受限 Planning / Governance
  • 模板和底座最小闭环
  • 诊断、审计、备份和签名升级

首期不承诺

  • 真正多人实时协作
  • 无边界全自动生产部署
  • 所有编程语言的完整 AST 本体
  • 任意第三方技能无审核安装
  • 云模型离线可用
  • 任意数据库迁移可自动逆向回退

1.4 用户与角色

产品基线是单一自然人用户。系统中的"专家、开发者、审核者"首期为逻辑执行角色，不等同多个登录账户。

2.2 三轴关系

Lunitide 由三条正交轴构成，它们协同支撑九阶段业务主链产出版本化产物。

轴一 · 五大智能内核

Ontology（语义骨架）、Memory（时间连续性）、Skills（能力库）、Planning（认知循环）、Governance（控制层）。五大内核不是五个阶段。

轴二 · 九阶段业务主链

需求调研 → 架构 → 方案 → UI → 数据库/接口 → 开发 → 测试 → 集成 → CR 发布部署。流程非机械全局串行，依赖产物批准且版本锁定时可并行。

轴三 · 横向平台能力

模型网关、模板、底座、接口、开发任务、测试、CR/部署、审计、诊断。

CHAPTER 03

信息架构

3.1 启动层与渐进式导航

默认启动页 MUST 为新对话，借鉴 ZCODE 的低干扰、对话优先和渐进展开方式，但不复制其品牌与组件外观。默认焦点进入多行输入框；最近会话/项目作为次级内容。

默认侧栏 ├─ 新对话 ├─ 最近会话 ├─ 项目 ├─ 工作区（阶段 / 计划 / 审批） ├─ 产物（文档 / 代码 / 发布） ├─ 资源（记忆 / 技能工具 / 模板底座） └─ 设置

九阶段进度、活动流与上下文详情只在进入项目或任务执行后按需展开；右侧栏默认收起。模型采用已配置默认值，未配置时才显示轻量引导。

3.2 完整功能地图（非默认平铺菜单）

项目 ├─ 项目总览 ├─ 九阶段工作区 ├─ 计划 DAG ├─ 会话 ├─ 文档与产物 └─ CR 与发布 能力中心 ├─ 项目本体 ├─ 记忆中心 ├─ 技能中心 ├─ 工具 / MCP └─ 治理与待审批 资产中心 ├─ 模板管理 └─ 底座资产 系统 ├─ 模型供应商与模型 ├─ 接口连接 ├─ 安全与策略 ├─ 日志与诊断 ├─ 备份与恢复 └─ 更新

3.3 对话优先的轻量开发工作台

Lunitide MUST 集成完整的代码开发闭环，但不得复制一套重型 IDE。默认主画布始终是对话；进入开发任务或点击文件、命令、预览、变更对象时，按需展开一个统一工作面板。

  • 对话主画布：目标澄清、实现说明、工具结果摘要、审批卡片和下一步动作。
  • 统一工作面板：文件、代码、终端、浏览器、变更五种互斥视图，支持关闭、轻览和聚焦三种状态。
  • 按需抽屉：计划、活动、上下文、审批详情；默认收起且不永久压缩对话。

长上下文、压缩与跨窗口续接

  • 百万 token 是逻辑容量，不是每轮直塞：单会话以固定版本的 canonical tokenizer 计量累计可重建内容，至少支持 1M tokens；每次请求另用当前模型 tokenizer 估算，由 Context Builder 按真实窗口、输出预留、工具预算和任务相关性动态装配。
  • 自动 + 手动压缩：接近窗口预算时后台生成新摘要版本；用户也可执行“压缩上下文”，预览压缩范围、摘要差异和保留项。压缩失败不得破坏当前可用上下文。
  • 类 Codex 续接：当前会话可“续接到新对话”，生成 Context Handoff；新对话展示来源、生成时间、覆盖消息范围和待办后再导入，且可返回原会话查证。
  • 保真与追溯：摘要和 Handoff MUST 结构化保存目标、关键决策及理由、硬约束、未完成任务、文件/符号/版本引用、工具与验证结果、风险和建议下一步；每个事实/状态/决策/约束/任务/证据 claim 均关联叶级来源，建议与推断须显式标型并保存推导来源。
  • 原文保留：压缩只新增派生版本，MUST NOT 改写或删除源 Message。只有用户显式发起的数据删除/保留期策略才可删除，并使所有摘要、索引和 Handoff 失效或重建。

请求预算利用率统一按 requiredTokens / effectiveWindow 计算：effectiveWindow = min(provider context window, input/output limit) - tokenizer safety margin；requiredTokens 包含 system、tool schema、选定上下文、当前输入、最大输出预留和工具续接预留。能力未知时必须采用保守默认值。

请求预算利用率默认动作用户感知
请求预算 < 70%近期消息 + 相关历史 + 引用按预算装配显示剩余上下文，不打扰
70%–85%预生成增量摘要、外置大工具输出、保留输出预算轻量提示“正在整理上下文”
85%–95%启用已校验摘要替换较老片段；可手动预览/重做显示压缩版本与可追溯入口
≥ 95%完成压缩并重新预算后再调用；仍超预算则返回 CONTEXT_BUDGET_EXCEEDED 并建议续接新对话不得用静默截断或越窗请求冒充成功
容量与分页解耦：消息列表单次 RPC/API 的 pageSize、payload 字节上限仅保护传输和渲染，不得实现成单会话消息数或 token 总上限；历史使用稳定 cursor 按 message.sequence 分页。
视图内置能力明确边界
文件任务相关文件、轻量目录树、搜索、加入上下文不默认递归展开整个仓库
代码语法高亮、单文件轻编辑、选区解释/修改、诊断、inline diff不自建完整 LSP、调试器和插件生态
终端Agent 命令与用户终端、流式输出、停止、重跑、解释错误任意 shell 不直接暴露给 Renderer
浏览器本地预览、导航、视口、截图、控制台/请求错误摘要不复制完整 DevTools
变更逐文件 diff、接受/撤销、增删行统计、任务与来源追踪提交、push、发布是独立风险动作
外部编辑器协作：首期支持将项目、文件、行列和 Diff 定位到 Visual Studio Code；后续通过 EditorAdapter 扩展其他编辑器。月汐保有任务、策略、工具运行和变更证据的权威状态。
模式语义：“协作 / 代码”不是两个割裂产品。切换只改变默认工具集、上下文预算和面板建议，不丢失会话、任务、计划或审批状态。

3.4 开发交互与权限分级

  1. 用户从对话描述任务，系统绑定项目、阶段、DevTask、来源产物与工作区根目录。
  2. Agent 先读取相关文件并提出计划；文件写入前创建 checkpoint，变更进入 ChangeSet。
  3. 命令、测试和浏览器验证以流式卡片回到对话，完整输出留在工作面板。
  4. 用户逐文件审查；应用到工作区不等于 commit，commit 不等于 push。
  5. 结果绑定 CodeChange、TestRun、ScanRun 和 TraceLink，满足门禁后进入 review/test。
能力默认策略示例
只读工作区内自动放行并审计列目录、读文件、搜索、Git status
可回退写入限定工作区 + checkpoint；按项目策略自动或确认新增/修改源码、格式化
本地执行命令规格/参数白名单；资源和时限约束lint、test、build、dev server
敏感副作用必须审批工作区外写入、安装依赖、联网命令、删除、Git push

作用域、保存与权威值

  • Engine 按 built-in default → application/workspace → project → Mandatory Policy 计算 effectiveValue；每项返回 source、inherited、overridden、managed/locked、version 和 applyMode。
  • 普通字段在 Renderer 内存形成 draft，调用 settings.validate 后由 settings.patch(expectedVersion,idempotencyKey,digest) 原子保存；禁止 localStorage 保存业务设置。
  • 外观可以临时预览；普通设置在一次保存成功后即时 apply；语言/运行时项准确显示 renderer_reload / app_restart，不得虚称已完全生效。
  • Key、删除、恢复、导出、更新和安全策略不进入通用 patch，继续使用专用安全对话框、Command RPC、Policy、影响摘要和执行前重验。
  • 断线导致结果不明时进入 outcome_unknown，UI 必须按 idempotency key 查询状态，禁止直接重复保存或执行。
设置中心完成门禁：每个公开设置必须有稳定 key、类型/schema、默认值、允许 scope、敏感级别、存储位置、merge/继承策略、applyMode、Policy 约束、RPC、事件、错误码、迁移和 E2E；仅在原型出现菜单或静态控件不算实现完成。

  • 产物包括 ERD、数据字典、接口契约、方向/字段映射、DatabaseContract 与 MigrationPackage。
修正：OData 是基于 HTTP 的标准数据服务协议。若需要数据库直连，应独立命名为 Database Connector；不得将连接串直连错误称为 OData。

5.10 阶段九：CR、发布与部署

CR MUST 绑定：

  • Git commit
  • 依赖 CR DAG
  • 测试证据
  • 制品 SHA-256
  • 版本、目标环境和回退策略

环境晋级与不可变包：同一个 ReleasePackage 同时包含代码制品与 MigrationPackage，按 development → test（可选）→ production 晋级；各环境使用同一 package digest，禁止按环境重打包。

发布编排：PromotionOrchestrator 固化门禁快照，按“只读契约预检 → 恢复点 → 向前兼容迁移 → 迁移后重扫 → 代码部署 → 健康与契约复核”顺序执行；这是一项代码与数据库绑定的发布事务，不是两者无序并行。数据库演进默认采用 Expand → Migrate → Contract，Contract 仅在旧版本已退出且兼容门禁通过后独立执行。

并发安全：v1 仅处理本机 Owner、Agent、VS Code 与文件监视器之间的编辑来源提示；所有修改携带 base hash/version，冲突采用三方合并，禁止长锁与 last-write-wins。短租约仅用于发布包冻结和环境导入，必须有 holder、TTL、续租与过期恢复。远端多人 Presence、身份与职责分离属于 ADR-011 Deferred。

变更失效：审批后任一绑定内容改变，CR 自动进入 changed_after_approval 并重新审批。
双领域隔离："Lunitide 自身更新"和"Lunitide 管理的用户项目部署"是两个独立领域，不共用含糊的版本/回滚承诺。

M2 Provider→Secret→真实对话纵向切片 · 固定验收序列

  1. Renderer 通过生成 SDK 调用 provider.list。
  2. Host 校验 CoreWebView2/source/frame/document nonce/schema/deadline 后，经认证 Named Pipe 转发。
  3. Engine 从 SQLite 查询脱敏 Provider，并返回生成的类型化响应。
  4. 新增/覆盖 Key 只经一次性 Bridge 输入窗口进入 Host SecretService，以 DPAPI 保存；已保存 Key 不回 Renderer。
  5. Go ModelGateway 对目标 Provider 执行真实连接测试与可取消流式调用。
  6. UI 展示 status / stage / httpStatus / latencyMs / errorCode / sanitizedMessage / correlationId，不得展示 Key 或未脱敏上游正文。
  7. 全链路产生 trace、append-only 审计与脱敏结构化日志，并通过非法 origin/schema、SSRF、Key canary 和取消测试。
  8. unit、contract、UI E2E、integration、security 与故障测试全部通过。
  9. 使用 M1 迁移契约从 0.2.1 原型迁移一个 DeepSeek Provider 配置与模型列表；Key 成功迁移或明确进入 requires_reentry，随后真实测试通过。
