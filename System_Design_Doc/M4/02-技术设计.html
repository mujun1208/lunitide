Profile 与 Prompt 正交设计

Profile 决定资源与能力视角，Prompt 独立编译管理，两者互不耦合、互不授权。三轴正交模型：Agent Profile 只改变角色、Prompt、候选工具与上下文偏好；Automation Level（Manual / Assisted / Full-Managed）只影响低中风险动作；Business Stage 采用 M7 固定九阶段 key（INITIATION_BOUNDARY / RESEARCH_EVIDENCE / REQUIREMENT_DEFINITION / SOLUTION_EXPERIENCE / ARCHITECTURE_PLAN / DEVELOPMENT_CHANGE / VERIFICATION_ACCEPTANCE / RELEASE_DELIVERY / OPERATIONS_RETROSPECTIVE），决定输入、产物与门禁；Policy Engine 始终对规范化的具体动作最终裁决，高风险 Review 不因任何轴变化而降级。

对象定义强制边界
AgentProfile身份与观察视角；可为用户提供的行业专家，或产品签名内建的产品设计经理、架构师、方案专家、UI 专家、需求专家、接口专家、数据库专家、业务逻辑专家、流程专家、代码专家。Profile 不是 Skill、ToolGrant、凭据或权限集合；固定官方专家只能随产品签名内建；ProfileVersion 不可变，运行时按 digest 固定。
Skill可组合的流程资源包：方法论、交付模板、检查清单、工作流约束及可选工具声明。Skill 不是人格；选择、组合或编排 Skill 不授予权限，每个 ToolCall 仍由 Policy/Review 裁决。
PromptBundle根模板版本、ProfileVersion、ExpertPrompt、SkillVersion 集合及结构化变量快照的不可变解析结果。canonicalize 后生成 promptDigest 并绑定 Run/Invocation/Evaluation/Audit；禁止自由文本拼接覆盖 system/policy。

根模板仅允许四个产品签名入口：lunitide-prompt.tpl（通用根）、lunitide-expert-prompt.tpl（显式 Role Override + ExpertPrompt 槽位）、lunitide-expert-working-prompt.tpl（专家工作调用）、lunitide-ask-prompt.tpl（澄清/问答）。PromptCompiler 只从 schema-validated 变量注入 profile、objective、stage、constraints、skillRefs、contextRefs、outputSchema、provenance，按固定转义/分隔规则输出 PromptBundle 与 digest；模板、Profile、Skill 或变量任何变化都产生新 digest。提示词、Role Override、行业标签和专家称谓不得提升权限、改变 Mandatory Policy 或绕过 Review。

行业专家解析：识别用户行业后，可在同一 Root Run 内构造临时行业专家，定义必须完整包含“系统提示 + 方法论 + 交付模板 + 工作流约束”，保存为临时 ProfileVersion 并通过受治理 AgentInvocation 使用；不得伪装官方专家、不得跨 Run 静默持久化。无论专家为何种身份，对用户只展示结论、假设、方法、证据与专家分歧，不展示私有思维链。
阶段协作与 Scope Seal 对齐：需求定义（REQUIREMENT_DEFINITION）与架构计划（ARCHITECTURE_PLAN）阶段由需求专家、架构师、行业专家三方评审；方案与体验（SOLUTION_EXPERIENCE）阶段由产品设计经理、方案专家、UI 专家及按需接口/数据库/业务逻辑/流程/代码专家组成专家组。M4/M5 必须由同一个单 Agent 在同一 Root Run 中顺序切换 Profile 并逐次记录受治理 Invocation，严禁伪造并行 Child；真正多专家并行、Child Run、fan-out/fan-in 仅 M6 启用，且在 Scope Seal 解除并满足 M5 安全门禁前必须不可达。

预算状态机

BudgetEnvelope 必须同时限制 model turns、tool calls、tokens、cost、wall-clock、output bytes、retries、no-progress 与 hard ceiling，不得用固定 20–30 步替代；任何子限额与 hard ceiling 到达均 fail-closed。预算随 Run 持久化于 agent_run.budget_json / used_json，创建时绑定 ResolvedConfigSnapshot 与 Policy digest，运行中策略收紧在下一动作前强制重验。

状态进入条件规则
granted 初始Run 创建按配置冻结各维度额度并写入 budget_json；无预算的 Run 不得进入 running。
in_use 扣减每次模型调用 / 工具执行先预留（reserve）再实际扣减（consume），usage 追加写 used_json，与 EffectJournal 同事务；崩溃后以持久化 used_json 为准对账，不凭内存重建。
warning 预警阈值任一维度达到可配置预警阈值仅向用户呈现剩余预算与建议（收敛范围、压缩上下文、提前收敛），不改变授权；禁止静默扩容或越限放行。
exhausted 耗尽阻断任一子限额或 hard ceiling 触达Run 进入 paused_budget；拒绝新的模型调用与受控 effect，已批准未执行的 ToolCall 不得借剩余额度继续；不得继续产生任何 effect。
resumed 恢复用户显式追加预算或收敛范围后 agent.run.resume追加额度必须落审计并更新 budget_json；恢复不回溯已拒绝的 effect；outcome_unknown 的扣减先对账再恢复，禁止盲重试。

预算终止是固定验收演示的一部分（注册 Workspace → 只读调查 → Plan → ChangeSet → 审批应用 → 恢复 → 触发预算终止，全程只有一个 AgentRun）；hard ceiling 超额执行必须为 0。多 Child 预算守恒与退款语义（granted = reserved + consumed + refundable）属 M6 BudgetAccount，M4 单 Agent 不引入。

安全边界

Bridge 校验 exact origin/top frame/document nonce/schema/deadline；模型、Renderer、网页正文均不可信。Command 默认无 shell，环境变量只引用 SecretRef，输出脱敏并限额。Web 每次重定向重新解析 DNS 并拒绝 loopback、私网、link-local、metadata、非允许端口与 rebinding。Job Object 是生命周期限制而非安全沙箱；M4 仅签名内建工具与明确授权可执行文件。

M4 canonical 状态与迁移裁决

Run 唯一枚举：queued|running|paused_review|paused_budget|completed|failed|cancelled|interrupted|outcome_unknown；succeeded 仅是 legacy 读取/UI 别名，禁止新写。ToolCall 的 waiting_review 投影到 Run 的 paused_review；changed_after_approval 是 guard reason，不是持久状态。SQLite 列约束必须写为 CHECK(parent_run_id IS NULL) / CHECK(delegation_id IS NULL)；历史 Child 数据进入只读隔离迁移报告，禁止静默清 NULL。
