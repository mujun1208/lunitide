五大智能内核

Ontology · Memory · Skills · Planning · Governance

五者合一，构成合格 AI 开发助手的完整内核。 本体提供语义骨架，记忆维持时间连续性，技能沉淀可复用能力， 规划驱动认知循环，治理作为不可绕过的控制层。任何一环缺失，系统都将在可验证性、可控性或上下文一致性上失稳。

THESIS · 核心论点

五块拼图，缺一不可

来源：统一设计 §15

Lunitide 不把 AI 助手视为单一的“对话模型”，而是五个相互约束的子系统。 它们共同回答一个问题：一次智能任务的输入如何被可信地转化为可审计的产出。

01 / ONTOLOGY
本体引擎
Ontology Engine
语义骨架。把代码、文档与产物结构化为版本化节点与边，提供可追溯的查询入口。
02 / MEMORY
记忆管理器
Memory Manager
时间连续性。分级保存工作态、会话摘要、确认事实与结构化知识，召回带回解释。
03 / SKILLS
技能系统
Skill System
能力库。显式与语义双通道匹配，匹配只产生候选，权限由治理层独立授予。
04 / PLANNING
规划与编排
Planner / Orchestrator
认知循环。输出带哈希的 DAG，按预算与依赖调度节点，副作用必须幂等且可验证。
05 / GOVERNANCE
治理
Governance
控制层。策略在执行前评估，强制确认不可绕过，模型与 Review Agent 都无权改写。
KERNEL 01

Ontology Engine · 本体引擎

语义骨架：把仓库快照转化为版本化、可查询、可回溯的节点边图。

来源：§15.1

职责与数据流

本体引擎负责一条单向流水线：源快照 → 解析 → 节点与边 → 版本化索引 → 查询。每一阶段都不可跳跃，任何查询结果都应能逆推回具体的源文件与 revision。

源快照 Snapshot → 解析 Parse → 节点 / 边 Graph → 版本化索引 Index → 查询 Query

关键规则

  • 增量索引按内容哈希：仅内容变更的文件触发再解析，避免全量重建。
  • 单文件失败不阻断：解析异常隔离在单文件粒度，记录失败原因后继续处理其余文件。
  • 查询返回来源与 revision：每个结果节点附带溯源指针，可定位到具体文件、行范围与提交版本。

候选 POC 范围

当前候选范围为 Markdown / JSON / Go / TypeScript 基础解析；最终首期范围以 ADR-006 批准结果为准。其他语言通过 parser registry 扩展注册，不在内核硬编码。

节点类型注册表

节点类型使用可扩展注册表，MVP 至少包括以下类型：

File Document Artifact Requirement Decision Module Class Function Interface Table Field UseCase TestCase Task Release
性能承诺的边界：不承诺 O(1) 查询。性能指标必须使用 P95 延迟和增量更新时间两项度量，不使用“O(1)”等绝对化宣传口径。
KERNEL 02

Memory Manager · 记忆管理器

时间连续性：四层分级记忆，每条记录都可溯源、可衰减、可回收。

来源：§15.2

四层记忆模型

working
当前 run 的临时状态，任务结束后即销毁或归档。
short_term
会话摘要，跨轮次保留对话脉络与近期上下文。
long_term
用户确认的事实、偏好、决策与情节，长期持久化。
semantic
由本体或事实结构化出的知识，跨会话可推理。

关键规则

  • 每条记忆必有元数据：来源、作用域、可信度、重要度与修订记录，缺一不可写入。
  • 模型推断不得自动升级为“已确认事实”：未经用户显式确认的推断只能停留在 working / short_term，禁止污染 long_term。
  • 召回带回解释：综合相关度、时效、重要度、可信度四维打分，并返回命中的字段与依据。
  • 删除需传播：单条删除要同步传播至结构化记录、向量、缓存与摘要，避免“僵尸记忆”。
隔离红线：跨项目泄漏率必须为 0。任何项目作用域的记忆都不得作为另一项目的上下文被召回，违反即阻断。
确认边界：模型推断不能自动升级成“已确认事实”。long_term 的写入权仅属于用户显式确认或治理层批准的操作，模型只能建议、不能直接落库。
KERNEL 03

Skill System · 技能系统

能力库：显式与语义双通道匹配，匹配只产生候选，权限由治理层独立授予。

来源：§15.3 / §12

Skill Manifest 字段

每个技能的清单文件至少包含以下字段，缺字段则校验失败：

name version publisher description triggers entrypoint input/output schema permissions dependencies timeout resource limits signature

匹配策略

  • 显式触发优先：用户通过命令、@提及等显式调用的技能直接进入候选。
  • 语义评分其次：对未显式触发的技能，按用户输入与 trigger 描述计算语义相似度。
  • 低于阈值回退：所有候选评分低于阈值时，回退为普通对话，不强行调用。
  • 并列高分提示选择：多个技能评分接近时，向用户提示并让其选择，不自动裁决。

安装与安全规则

  • 哈希校验：安装包与已发布清单的内容哈希必须一致。
  • 签名验证：技能必须经可信签名，未签名或权限扩大的升级默认进入 quarantined。
  • 依赖锁：依赖列表锁定版本，避免隐式升级带来的供应链风险。
  • 权限差异与撤销：升级时若权限集合扩大，须用户重新授权；提供一键撤销与卸载机制。

Skill 状态机

Skill Lifecycle
draft → validated → installed → enabled
enabled ⇄ disabled
enabled → quarantined → uninstalled
enabled 可被匹配调用 disabled 用户手动停用 quarantined 未签名/权限扩大，隔离待审 uninstalled 彻底移除
权限边界：匹配不授予权限。技能命中仅表示它成为候选执行单元，是否真正被调用、调用时的资源与数据边界，完全由 Governance 层在执行前独立评估。
KERNEL 04

Planning / Orchestrator · 规划与编排

认知循环：Planner 输出带哈希的 DAG，Orchestrator 按预算与依赖调度节点。

来源：§15.4 / §13

Planner 与 Orchestrator 分工

  • Planner 输出 DAG 及 graph hash：计划以有向无环图表示，并保存为带版本的 PlanVersion，可被回放与审计。
  • Orchestrator 三条调度规则：仅当节点同时满足依赖满足、策略允许、预算充足三个条件时才被选中执行。

预算维度

预算不是单一阈值，而是六个维度的联合约束，任一维度触顶即熔断：

max_model_calls
最大模型调用次数
tokens
输入 / 输出 token 上限
cost
费用上限（按计费币种）
wall_clock
墙钟时间上限
tool_calls
工具调用总次数
parallelism
最大并行节点数

副作用节点约束

凡产生外部副作用的节点（写入文件、调用 API、执行命令等）必须满足三条硬性要求：

  • idempotency key：携带幂等键，重试时不会重复生效。
  • 风险等级：标注 risk 等级，决定是否触发 Review。
  • 可验证完成条件：定义 acceptance 条件，Orchestrator 据此判定真正成功。

Plan / Node 状态机

Plan Node Lifecycle
● → queued → running → waiting_approval
waiting_approval →approved + hash matches running 　 waiting_approval →rejected / expired cancelled
running → succeeded 　 running →retryable retrying → running
running → failed 　 running →engine crash interrupted →safe resume queued
succeeded 达成 acceptance failed 不可重试失败 retrying 可重试失败后回到 running interrupted 引擎崩溃，仅幂等节点可恢复 cancelled 被策略拒绝或过期
反思熔断：反思不得无限循环。达到重试上限或预算上限后必须熔断，转为请求人工决定，禁止“再试一次”的无限递归。
KERNEL 05

Governance · 治理

控制层：策略在执行前评估，强制确认不可绕过，模型与 Review Agent 都无权改写。

来源：§15.5 / §13.2

Policy 输入与输出

维度字段
输入actor、project、operation、resource、normalized args、data classification、tool trust、environment、plan version
输出allow / deny / require_review + reason + policy version

每一次策略判断都写审计，采用 append-only + hash chain，用户可验证完整性。审批只对不可变摘要生效——摘要一旦哈希不匹配，原批准即失效。

强制确认操作（即使全托管模式）

以下操作无论用户选择了多高信任等级，都必须经过显式 Review，不得自动执行：

  • push、发布、生产部署：任何向远端仓库或生产环境的不可逆发布动作。
  • 破坏性数据库或文件操作：DROP、DELETE、批量覆盖、不可逆文件删除等。
  • 凭据导出、跨域发送敏感数据：密钥、令牌、PII 等跨信任域流转。
  • 执行未信任代码或扩大技能权限：运行未签名或隔离态代码、提升技能权限集合。
  • 修改安全策略、审计或更新信任根：任何试图改写治理规则自身的动作。

Review 状态机

Review Lifecycle
● → pending
pending → approved 　 　 rejected 　 　 changes_requested
pending → expired 　 　 cancelled
approved → executing → executed 　 　 execution_failed
pending 待审 approved → executing → executed 批准并完成 changes_requested 需修改后重提 expired / cancelled 失效或取消 execution_failed 批准后执行失败，单独记录
冲突裁决：规则冲突取更严格者。当多条策略对同一操作给出不同结论时，系统按“最严优先”原则裁决，而非按优先级或时间顺序择一。
不可改写红线：模型和 Review Agent 都不能修改系统强制策略。治理规则属于信任根的一部分，任何模型输出、Agent 建议都不得直接写回策略库，必须经由独立的人工治理流程。
