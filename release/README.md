# Windows release security policy

`Build-Release.ps1` stages the native Go executables, WebView2 loader, renderer assets, and license notices. It does not copy large ML runtimes, omni/Comni/GGUF payloads, or other excluded roots into `release/out`. `Verify-Layout.ps1` rejects those payloads, every other root, and known Electron, Node, and Python runtime patterns, applies positive asset-extension allowlists, rejects disguised PE/ZIP/CAB content, requires Desktop and Engine to report the exact requested version, then requires `SHA256SUMS.txt` to describe every staged payload file exactly once with no missing or extra entries.

The WebView2 NuGet package hash and independently pinned x64 loader hash are source-controlled. The loader is not the Evergreen Runtime; Runtime availability remains a clean-machine prerequisite. The build verifies the package with installed `nuget.exe`, or fetches a version-and-hash-pinned verifier when none exists; package verification failure stops the build. Installer creation requires signing by default. `-AllowUnsignedDevelopment` produces a non-publishable rehearsal candidate. Production/tag builds require a clean committed checkout, sign all four owned executables before manifest generation, then sign the installer. Publisher acceptance requires an exact 40-hex certificate match, a timestamped Authenticode signature, and successful Windows SDK `signtool verify /pa /all /v` validation.

The installer defaults to `%LOCALAPPDATA%\Programs\Lunitide`, but interactive installs may select another writable directory on a local fixed drive, including `D:`. Silent installs use `/D=<absolute-path>` as the final argument. Existing installations upgrade only at their registered location; uninstall first if relocation is required. The installer rejects downgrade by default; `/ALLOWDOWNGRADE` is the explicit override. Before replacing files it accepts only a valid ownership marker, or a legacy uninstall registration whose `InstallLocation` exactly matches the selected path. Staging and rollback directories are siblings on the selected volume, process stopping and uninstall are scoped to the registered location, and user data is never placed in the program directory. Uninstall retains `%LOCALAPPDATA%\Lunitide` unless `/PURGE` is explicitly supplied. Transaction diagnostics are persisted under `%LOCALAPPDATA%\LunitideInstaller\Logs`.

`Test-Install.ps1` intentionally exercises the real per-user Windows Known Folder paths. It refuses to run when an existing Lunitide install, registration, or data root is present, launches the installed product, waits for the trusted WebView2 document to load, closes the real window with `WM_CLOSE`, and verifies that Desktop and Engine exit cleanly. Use it only in a disposable Windows account or clean VM because a real window, shortcuts, HKCU uninstall registration, and application data root are exercised.

On a machine without a compatible Evergreen Runtime the installer logs `code=W140` (absent) or `code=W141` (older than the pinned minimum) to the persisted install log, presents an acquisition guide page with the official download link, a re-check action, and an informed continue option, and the desktop then fails closed with an explicit runtime-missing dialog and a non-zero exit instead of a window flash; the isolated browser host is unreachable in that state because the desktop never starts.

`Test-AcceptanceMatrix.ps1` binds these behaviors to one JSON evidence record per clean-machine cell: Windows 10 x64 and Windows 11 x64, each with the Runtime present and absent. Every run captures OS caption/build/architecture, Runtime version, PowerShell version, source commit, installer SHA-256, signature status, signer thumbprint, and timestamp presence. A present-runtime cell delegates the full install/upgrade/retain/reinstall/purge lifecycle to `Test-Install.ps1`; an absent-runtime cell (`-ExpectRuntimeAbsent`) asserts the silent install logs `W140`, the desktop fails closed with the runtime-missing dialog and a non-zero exit leaving no engine processes, and purge uninstall removes both install and data roots. Signed cells require `-ExpectedSignerThumbprint` plus `signtool verify /pa /all /v`; `-AllowUnsignedDevelopment` produces rehearsal-only evidence. Evidence defaults to `matrix-evidence-<build>-wv2-<state>-<utc>.json` beside the script (`-EvidenceOut` overrides), each cell must run on a fresh disposable account or VM, and release evidence for all four cells must bind to the same commit and installer digest.

The executable inventory is `Lunitide.exe`, `lunitide-engine.exe`, `lunitide-maintenance.exe`, and `purge-user-data.exe`. Tray mode uses the desktop executable; document parsing uses the engine's `--doctext-worker` entry before bootstrap/secret access. Maintenance is an offline backup/verify/restore tool. Installation refuses to terminate active maintenance; finish it before upgrading or uninstalling. Default uninstall retains the data directory. Install directories overlapping that data directory, or containing directory junctions/reparse points, are rejected.

Every build needs a new empty `OutputRoot` below `release/`; existing candidates are preserved. `SOURCE-CANDIDATE.json` records commit, exact source-file hashes, the combined source digest, executable inventory, and signed/rehearsal mode. Inputs are checked before and after build/package work. This detects concurrent edits; it is not a substitute for a trusted build machine or reproducible-build attestation. Copy the candidate digests to the review record before acceptance. `Verify-Release.ps1` now requires `-ExpectedInstallerHash` and `-ExpectedSourceTreeSha256` from that record, in addition to `-OutputRoot`, `-Version`, and the publisher thumbprint (or explicit rehearsal flag). CI saves these digests in a separate step before install tests and rechecks them before upload.

For matrix runs, supply `-SourceCandidate <stage/SOURCE-CANDIDATE.json>` and `-ExpectedSourceTreeSha256 <recorded digest>`; the recorded commit comes from the candidate, rather than whichever checkout happens to be on the test machine. Existing evidence files are never overwritten. `Test-Install.ps1 -TestRoot` is now a parent for a newly owned temporary child, and never deletes the caller's supplied directory.

`Test-ReleaseTools.ps1` validates scripts, source drift/tampering rejection, path boundaries and actual directory-junction refusal in isolated temporary directories. It builds the maintenance executable, checks AMD64 PE format and invokes only `-h` (before data-root preparation). It performs no installer run, signing, registry mutation, application launch or user-data operation.

For the user-run stability check, start the accepted application and the planned workload, then run `Test-Soak.ps1 -InstallDirectory <path> -ExpectedVersion <version> -ExpectedManifestHash <recorded stage SHA256SUMS hash> -EvidenceDirectory <new directory> -DurationHours 8 -ExpectedSignerThumbprint <publisher>`. The script only observes matching processes and writes resource samples; it does not send prompts, control the desktop, or touch application data. It reports process changes/absence and growth beyond configurable thresholds. An observed-stable result does not certify workload correctness. Complete the pending cases in `manual-acceptance.template.json` with real evidence, including actual providers, three voice routes, meetings, computer control, knowledge refresh, extensions, offline recovery and final shutdown. Scores remain unassigned until those cases are executed and reviewed.
